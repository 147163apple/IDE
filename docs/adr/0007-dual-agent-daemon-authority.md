# ADR-0007: 双 Agent 分权与 Daemon 单一权威

> **状态**: ACCEPTED
> **基线**: 架构规范 v1.6.1（commit `4280de6`，2026-10-24）
> **源自**: 《系统架构设计规范》§8 ADR-007
> **相关**: ADR-0001（分层适配）、ADR-0005（验证权威）、[`../rfc/v0.2-multi-agent-pipeline.md`](../rfc/v0.2-multi-agent-pipeline.md) §7.1 逻辑职责 vs 实际进程

## 背景

系统的核心张力是：**提出建议的人，不能同时是批准建议的人**。

如果让同一个 Agent 既「编译需求成合同」又「批准合同」又「执行并自评」，那么所有门禁都退化为自我审查，安全性归零。反之，若把权限打散到多个进程，又会立即引入跨进程状态同步、消息重放、超时补偿与双写一致性问题——其故障面远大于收益。

## 决策

**三权分立，且不必也不应该等于三个进程：**

| 角色 | 职责 | 权限边界 |
| :--- | :--- | :--- |
| **Supervisor** | 建议、翻译、编译草案、质疑自查提案 | **零执行权**：不可签发 Token、不可写用户项目主干、不可自批合同 |
| **Coding Worker** | 在隔离 Worktree 与 Scope 内施工与自测 | **零审批权、零判卷权**：不可自我点亮、不可合并、不可扩 Scope |
| **Daemon** | **独占**全部决策：状态机裁决、受控写盘、凭证签发/吊销、物理验证、合并放行 | 唯一权威；不做产品判断，不替用户点「确认开工」 |

三条补充纪律：

1. **隔离强度来自能力收窄，不来自进程数量**。需求 AI 与 Supervisor 允许共用模型与会话通道；Daemon 与受控执行器在 v0.1 已在同一宿主进程内共存——这是被允许的。
2. **Daemon 必须是确定性宿主程序**。权限判定、路径校验、退出码解读、合并放行中任何一项均不得交由 LLM 完成，也不得依赖 LLM「自觉遵守」权限声明。
3. **判定口径**：若某一安全属性在移除 Prompt 中的相关措辞后仍然成立，则该属性由系统实现；若随之失效，则该属性只是提示词修辞，**不构成本规范意义上的安全边界**。

## 后果

**正面**：获得了一条可被机械检查的权力边界；`tests/unit/dispute-triad.test.ts`、`daemon/supervisor/rules-l0.ts` 等可据此做负向断言。

**代价与约束**：
- Supervisor 的所有产出都必须走「提案 → 用户拍板 → Daemon 裁决」三段，交互链路比「一句话直接干活」长，必须靠 UI 折叠（决议区 / 采取推荐）把体感压回去；
- 「逻辑分权但允许同进程实现」的角色边界容易被后续维护者无意跨越，因此每次 UX 打磨卡都要复述「不改变分权」这一约束。
