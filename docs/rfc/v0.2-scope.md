## 1. 主题

**v0.2 主题 = 架构感知层**：让系统「看得见」项目的文件级依赖结构，并让这份结构在多 Worktree 施工时保持新鲜，最后交给用户可视化圈选 Scope。

主链只有一条，按依赖顺序推进：

```text
TASK-B.1  本地 AST 增量依赖图（数据层）
   │  硬依赖
   ├──────────────►  TASK-C.4  架构雷达视图 + Scope 圈选抽屉（呈现层）
   │                     ▲
   ▼                     │ 软依赖（新鲜度信号，可后接）
TASK-B.2  多 Worktree 监听 + Evidence STALE 联动（新鲜度层）

可选层：TASK-S.3  Supervisor HUD 建议流 / WebSocket 广播（激活与否由 Tina 定）
不在本 RFC：TASK-D.1e  桌面壳 / 真·选文件夹（维持 DEFERRED，另立 RFC）
```

## 2. 「激活 ≠ 开工」

本 RFC 里的「激活」只表示**进入 v0.2 范围**，不表示可以施工。每张被激活的卡开工前仍须依次通过：

1. **DoR 重写**：按 `task-card-standard.md` R-1～R-12 与 `../templates/05-task-card.md` 样板重写卡正文（现有正文均为 2026-10-20 前的短卡，未过 DoR）。重写本身只改文档、状态不变。
2. **Tina 单卡授权**：DoR 重写合入后，由 Tina 对该卡单独授权，才由 `[DEFERRED]` 改为可开工状态。

先例：`TASK-W.5b`（P-124 DoR 重写 → P-125 合入回写）、`TASK-W.9`（拆 W.9a/b/c，W.9c 以「READY，待 Tina 单卡授权」挂 Sprint 首要，P-131～P-134）。本 RFC 沿用同一流程，不开批量授权口子。

## 4. 逐卡说明

### 4.1 TASK-B.1 · 本地 AST 增量依赖图（建议激活）

- **激活理由**：B.2 与 C.4 的共同数据源；没有它，Scope 圈选只能靠用户手写路径，Supervisor 也无法回答「改这个文件会波及谁」。纯 daemon 内核、无 UI、可独立测，是 v0.2 风险最低的起点。
- **依赖边**：前置 `TASK-D.1`（COMPLETED）。下游：`B.1 → B.2`、`B.1 → C.4`（**硬依赖**）。
- **验收口径（性能指标）**：
  - 规模：1000 个源文件节点（`src/**/*.{ts,tsx,js,jsx,mjs,cjs,json}`，统一路径前缀 G-16）。
  - 冷启动全量建图 ≤ **1500ms**；单文件增量修补 ≤ **20ms**。
  - DoR 重写需补齐测量口径：固定合成夹具（节点数 / 平均出边数）、取多轮中位数还是 p95、计时边界（是否含读盘）、CI runner 档位（ubuntu-latest / macos-latest；Windows 不作硬门）。
  - FAIL：内存泄漏、循环依赖导致死锁或无限递归。

### 4.2 TASK-B.2 · 多 Worktree 监听 + Evidence STALE 联动（建议激活，排在 B.1 之后）

- **激活理由**：v0.1 已支持多 Worktree 施工，但 Evidence 只在合并前指纹复核时才发现过期。B.2 让「外部改了文件 → 证据作废」实时可见，是 C.4 雷达能显示「哪里已失效」的前提。
- **依赖边**：前置 `TASK-B.1`、`TASK-A.1`（COMPLETED）、`TASK-A.6`（COMPLETED）。对 C.4 为**软依赖**（C.4 可先只读静态图，再接新鲜度信号）。
- **验收口径（STALE 窗口语义）**：
  - **窗口定义**：从「非忽略目录内文件写入落盘」到「Evidence 状态变为 `STALE`（携带 `E_EVIDENCE_STALE`）、`can_merge = false`、广播 `EVIDENCE_STATUS_CHANGED`」。目标在 watcher debounce 窗口内，性能目标 ≤ **50ms**。
  - **50ms 是体验目标，不是安全门**：安全性只由**合并前指纹复核兜底**保证——监听丢事件、系统负载、debounce 合并都不允许让过期证据合入。验收必须分别测两条：实时路径（≤50ms，可软判）与兜底路径（必须硬判）。
  - **忽略目录**：`.git/`、`.stagent/`、`node_modules/`、`dist/`、`build/`、`coverage/` 写入不得误报。
  - DoR 重写需写清：debounce 窗口的默认值与可配置范围；窗口内多次写入只算一次失效；STALE 只能由重新核验清除，不能由「改回原文件」自动恢复（或明确相反裁决）。

### 4.3 TASK-C.4 · 架构雷达 + Scope 圈选抽屉（建议激活，排在 B.1 之后）

- **激活理由**：架构感知层面向用户的唯一出口；把「白名单路径」从文本框变成在图上圈选，降低非技术用户定义 Scope 的门槛。
- **依赖边**：前置 `TASK-C.3`（COMPLETED）、**`TASK-B.1`（硬依赖：没有依赖图就没有雷达数据）**；`TASK-B.2` 软依赖（新鲜度着色）。
- **验收口径（节点规模）**：
  - 1000 节点拓扑可渲染；局部 patch ≤ **16ms**（60 FPS）；前端内存增量 ≤ **30MB**。
  - 超过 1000 节点时的降级策略（聚合到目录层 / 分页 / 拒绝渲染并提示）需在 DoR 重写中裁定，不得静默卡死。
  - 治理断言（硬判）：已批准合同上圈选 Scope **强制派生新 Revision 并重新审批**，禁止原地扩权。
  - DoR 重写需写清：雷达挂在哪个 Tab（沿用「按需打开的可关闭 Tab」约定）、与既有任务图谱（C.10 系）的分界。

### 4.4 TASK-S.3 · Supervisor HUD 建议流（可选层，激活与否由 Tina 定）

- **为什么是可选**：S.3 不在 B.1 → B.2 → C.4 链上，也不被它们依赖。旧设计实现仅存于未合并分支 `wip/s2-s3-supervisor-old-design`，卡状态带 `[REWORK]`，且「状态 / 草案推送需改接 L0 规则引擎后再评估」。
- **若激活**：建议只做 B.2 产生的 `EVIDENCE_STATUS_CHANGED` 等**事实帧**的 HUD 展示，不复活旧成熟度帧；鉴权口径沿用 D.1「仅鉴权连接可收帧」。
- **若不激活**：维持 `[DEFERRED → v0.2+]`，不影响主链验收。
- **待 Tina 决定**：激活 / 不激活；激活时范围是「仅事实帧」还是含建议帧。

### 4.5 TASK-D.1e · 桌面壳 / 真·选文件夹（维持 DEFERRED）

- 维持 `[DEFERRED → v0.2+]`（P5.8）。桌面形态（Electron / Tauri / 本机助手）涉及打包、签名、更新与鉴权注入，体量与架构感知层无关，**另立 RFC，本文不展开**。
