## 1. 目标与核心原则

当用户打开一个已经开发并运行的项目时，Studio 不应把「尚无本轮合同」呈现成「项目什么都没有」。它可以帮助用户了解当前项目，并为后续需求讨论提供背景；但不能把静态扫描结果包装成历史施工合同、验收结论或质量保证。

核心原则：

1. **区分现状事实与质量结论。** 扫描发现某路由、文件或模型定义，只能说明代码中存在相应痕迹，不能证明功能可用、数据正确或没有漏洞。
2. **区分全景资产与本轮施工。** 系统图谱描述项目当前结构；正式微合同的任务图谱描述本轮约定的改动和验收工作。两者不可互相替代。
3. **来源可追溯，未知如实呈现。** 每项发现应注明来源、扫描基线及置信/验证状态；推测不得伪装成确定事实。
4. **只读承诺必须与实际机制一致。** 若扫描没有执行代码、启动服务或写入文件，界面可以明确说明；未经实现与测试证明，不应承诺「绝不触碰真实数据」或「完全只读」。产品意图已定：**打开即自动深扫、全程零弹窗**；工程职责收口（目标机制，证明前不作硬承诺）为扫描器在 **只读挂载 + 物理断网 + 约 3 秒超时熔断** 的轻量沙盒内运行，并禁止动态执行项目脚本（Webpack/Vite 配置副作用、加载 `.env` 触发外网、CLI 插件 init 等）。目标 UX 文案：「正在为您安全探查项目结构（纯本地只读分析，不触碰线上业务）」——属目标表述 + 必达机制要求，机制实现与测试证明前不得当作已兑现承诺。
5. **用户确认基线不等于签署施工合同。** 基线确认仅表示用户认可或接受这份现状快照作为后续讨论参考，不代表接受质量担保、授权改代码或确认所有扫描推断正确。

## 2. 项目现状基线档案与正式施工合同的边界

产品主名定为 **「项目现状基线档案」**（见文首 Tina 定案）。「Contract #0」仅保留为历史讨论别名；若文案中出现，必须始终带有「只读现状档案，非施工合同」的解释，不得单独作为产品主名。

| 维度 | 项目现状基线档案（历史讨论别名：Contract #0） | 正式施工微合同 |
|---|---|---|
| 目的 | 描述某一时点可观察到的项目结构与分析结果 | 约定一轮明确的改动、边界、验收条件与授权 |
| 主要输入 | 导入/打开的项目内容、可访问的仓库与分析工具 | 用户确认的需求、澄清答案、方案、Scope、断言及 Demo 等约定资产 |
| 能够表示 | 扫描时点、代码/文件指纹（若已实际采集）、静态发现及其来源 | 本轮要改什么、不改什么、如何验收，以及对应的授权状态 |
| 不能单独证明 | 既有功能正常、历史测试通过、生产环境与本地一致、无安全问题 | 超出已定义和已验证证据范围的质量、安全或运行承诺 |
| 用户操作 | 审阅、纠正、确认作为后续参考，或暂不确认 | 明确签署/授权，按合同流程进入施工 |
| 状态含义 | 基线待审阅 / 已确认（名称与状态机兼容仍待定） | 按正式状态机流转；不能用基线状态冒充施工状态 |

### 2.1 基线档案可支持的陈述

只有在相应信息确实被采集并留有可复核来源时，基线档案才可陈述：

- 在某次扫描中发现了哪些文件、目录、配置或代码声明；
- 在静态代码中发现哪些路由定义、模块引用、数据模型声明或测试声明；
- 可访问的 Git 仓库在扫描时报告的分支、提交标识和历史记录；
- 扫描使用的工具、版本、范围、时间、忽略规则及未能读取的部分。

这些是「扫描观察结果」，不是对运行中系统的全面陈述。每一项都应允许显示「未探测」「无法确认」或「扫描不完整」。

### 2.2 基线档案不得暗示的结论

不得仅凭静态扫描宣称：

- 某业务功能已经正确实现或通过验收；
- 既有测试当前通过，或测试覆盖足以保护业务；
- 本地模型与生产数据库同步，或生产数据已被检查；
- 外部服务可连接、凭证有效或生产集成正常；
- 项目不存在 Bug、漏洞、数据风险或未发现的依赖；
- 后续合同的 Scope 已天然安全，或所有未列入范围的代码都已被技术机制保护。

「基线确认」本身也不构成对扫描准确性的绝对保证，不能替代用户审阅、运行验证或后续合同验收。

### 2.3 工作区洁净度检查（Workspace Dirty Check）

基线档案的存量材料中，**必须强制包含**一项「工作区洁净度检查」：

- 记录扫描时点是否存在 `uncommitted changes`（未提交改动）或 `untracked files`（未跟踪文件）；
- 若工作区不洁净：基线档案打上 **黄色警示**，并提示类似：「发现本地存在 N 个未提交/未跟踪文件。后续首张微合同将默认排除这些文件，防止被施工误覆盖。」
- 与现网「未跟踪文件属高危越界面」的门禁精神对齐（参见既有 S.4 / `E_OUT_OF_SCOPE_UNTRACKED` 一类约定）：基线只**记录与警示**，不自动把未跟踪文件纳入本轮可写范围；正式 Scope 白名单与越界门禁仍只认本轮施工微合同。

## 3. 五类材料的可靠反推范围与盲区

| 材料 | 可较可靠反推的内容（须注明工具和范围） | 不能仅凭该材料确认的内容 |
|---|---|---|
| 文件树 | 扫描时可见的路径、文件类型、目录分布、部分资源清单 | 文件是否仍被使用、是否可删除、真实模块边界、未挂载或忽略内容 |
| 路由与端点定义 | 静态可识别的路由声明、HTTP 路径/方法、部分中间件或守卫引用 | 页面是否能正常渲染、运行时路由是否可达、权限是否真正有效、边界输入行为 |
| 数据模型与迁移 | 仓库中声明的表/字段/类型/约束/迁移脚本 | 生产数据库的实际结构、数据质量、迁移是否已执行、业务不变量是否成立 |
| 测试文件 | 测试框架线索、测试文件与声明数量、可静态识别的目标 | 测试能否运行或通过、断言是否有意义、覆盖是否充分、测试环境与生产是否一致 |
| Git 历史 | 当前可访问仓库中的提交、分支与时间信息；按提交内容计算的变更热点 | 提交说明是否准确、历史代码是否正确、设计意图、仓库外改动及未提交内容的完整历史 |

扫描结果应分别记录：**观察到什么、从何处观察、覆盖了什么、未覆盖什么、哪些结论仍未知**。测试数量、路由数量等统计不得脱离扫描范围单独呈现为质量评分。

## 4. 两类图谱，不混用状态

### 4.1 系统结构图谱（System Graph）

面向项目结构与影响分析，节点可包括文件、模块、路由/端点、模型/表等；边表示可由工具支持的静态关系，例如 `imports`、`declares-route`、`references-model`。边必须区分「源码中直接观察到」与「工具推断」，不把静态引用自动解释为运行时调用或业务依赖。

图谱适合作为后续影响分析的**证据输入之一**，不能单独成为 Scope 白名单或越界防护的权威来源。正式 Scope 与门禁仍需由合同流程明确并由实际机制验证。

### 4.2 功能基线图谱（Functional Baseline Graph）

面向非技术用户展示可能存在的业务能力，例如「登录」「商品浏览」「结算」。其节点通常由路由、模块名、文案、代码结构等线索综合归纳，属于**候选能力描述**，不能默认等同于已验证功能。

建议节点允许用户确认、改名、合并、拆分或标记「不适用」。用户确认表示认可该描述可作为沟通标签，不等于功能已验收。

节点点击展开时，统一显示两行白话辅助说明（示例）：

- **来源线索：** 代码文件 `routes/order.ts` + 历史提交记录（按实际 `source_refs` 填充）
- **状态说明：** 已识别模块结构，但未经自动化测试验证

### 4.3 来源与状态标注

每个节点、边和总结项至少保留：

- `provenance`：来源类型（例如静态代码、配置、测试声明、Git 元数据、模型归纳、用户确认）；
- `source_refs`：可定位的路径、符号、提交或扫描记录（按产品权限适当展示）；
- `scan_id` / 基线指纹：它属于哪次扫描；
- `confidence` 或更清晰的认识状态；
- `verification_status`：静态发现、推断待确认、运行未验证、已由特定测试验证等。

置信度不能替代证据类型。建议在界面上优先用白话标签而非单独展示百分比：

- **代码中直接发现**：静态证据可定位；
- **根据代码线索归纳**：业务含义是推断，待用户确认；
- **尚未运行验证**：运行行为未知；
- **外部服务线索**：发现 SDK/配置痕迹，不代表连接成功；
- **用户已确认名称/含义**：仅确认描述，不代表质量验收。

避免用绿勾或「已完成/正常/安全」等容易被理解为验收背书的状态。颜色只能辅助，不能成为唯一解释。

## 5. 导入已有项目后的用户旅程

### 阶段 A：打开项目与说明探查范围

- Studio 保持既定外层结构，不因「已有项目」自动伪造施工合同、施工进度或已完成图谱。
- 按 Tina 定案：打开已有项目即 **自动深扫、零弹窗打扰**；全景视角展示「正在整理现状」或目标文案「正在为您安全探查项目结构（纯本地只读分析，不触碰线上业务）」（后者在沙盒机制证明前仅作目标 UX，见原则 4 / §7）。
- 说明本次会读取哪些内容、是否执行代码、是否写入文件，以及当前不能检查的环境。不要靠弹窗「防风险」；风险由工程沙盒收口（只读挂载 + 物理断网 + 约 3 秒超时熔断；禁止动态执行项目脚本）。
- 仅在产品机制已实现并验证后，才可把上述只读话术当作已兑现承诺。自动扫的产品意图已定；沙盒可证明性仍见 §7。

### 阶段 B：两段式渐进扫描（Progressive Baseline Scan）

「尽量全」不得以卡死右栏为代价。扫描采用两段式渐进策略：

| 时段 | 层 | 做什么 | 用户体感 |
|---|---|---|---|
| T+0～2s | **P0 快速骨架** | 秒级完成 `package.json` + 文件目录 + 顶层路由抽取 | 中栏立刻亮起基础全景卡片；**右栏 Supervisor 立即解锁可对话** |
| T+2～15s | **P1/P2 深度分析** | 后台异步流式跑 AST 依赖图谱、语义聚类等 | 节点在图谱中平滑「亮起」；进度文案描述真实步骤 |

- **深度分析未跑完，也不阻塞用户在右栏直接提需求。**
- 进度文案应描述真实发生的步骤，不编造百分比或精确完成时间。扫描范围、错误、跳过项和中断情况可查阅。扫描失败或部分完成时保留部分结果，并明确标为不完整，不把缺项解释成「未发现风险」。
- 首版呈现范围按 Tina 定案尽量全（结构图、功能图、测试统计等均可出现），但仍须遵守「观察 ≠ 质量结论」——统计数字不得包装成质量评分。
- 扫描开始时应同步做 **工作区洁净度检查**（见 §2.3）；若脏，黄标进入基线档案，不打断 P0 骨架呈现。

### 阶段 C：审阅现状档案与候选图谱

用业务语言呈现扫描观察和推断，并允许展开来源。明确区分：

1. 代码/配置中直接发现的结构；
2. 推断出的业务能力；
3. 尚未运行验证的行为；
4. 无法访问或无法确认的环境、数据、外部集成。

不要把「发现 N 个测试」写成「测试覆盖良好」，也不要把「发现集成 SDK」写成「服务已接通」。

### 阶段 D：用户审阅与确认基线

用户可以确认、修正或暂不确认。确认按钮文案统一为：

> **「认可此基线作为后续参考」**（Accept as Baseline）

**不要**使用「确认无误」——非技术用户无法验证「无误」。确认动作的精确含义示例：

> 「我已审阅这份现状记录，并同意将其作为后续需求讨论的参考。我理解其中的推断与未验证项不代表功能验收或质量保证。」

不要要求用户确认其无法判断的技术事实，也不要通过一组宽泛复选框暗示用户为扫描结果背书。必要时分开确认「作为沟通参考」与「允许后续执行某项操作」。

### 阶段 E：从基线进入第一张正式微合同

用户提出需求后，Supervisor 将基线作为上下文，继续需求澄清、影响分析、Demo（若适用）、合同 Scope 与验收断言编制。正式合同必须重新明确本轮改动、保护边界、风险、证据与授权；不能仅凭基线确认自动授权施工。

全景视角与施工视角应并存且命名清晰：前者展示项目现状结构，后者展示本轮合同的任务与验收进度。用户可以理解为「整座建筑的地图」和「这次施工单」，但不得暗示局部图谱已经覆盖或验证整座系统。

## 6. 主要误解与风险控制

| 可能误解 | 风险 | 设计与文案控制 |
|---|---|---|
| 全景图中的模块代表质量已验证 | 用户把结构发现当成质量担保 | 中性状态与明确注记；显示来源与未验证状态；不用验收绿标 |
| 功能图谱等于实际可用功能 | 推断被当成事实 | 标「根据代码线索归纳，待确认」；支持修正；不称「已实现/正常」 |
| 基线确认就是签署合同 | 用户误以为已授权改动 | 将基线确认与施工授权分开；按钮统一「认可此基线作为后续参考」，禁用「确认无误」 |
| 静态基线能保护整个老系统 | 过度承诺防越界或防回归 | 说明快照是记录而非防护机制；具体保护能力以合同和已验证门禁为准 |
| Demo 操作会读写真实数据 | 数据恐慌或真实副作用 | 只在隔离机制确实成立时声明数据边界；否则不得用「绝不触碰」承诺，先说明实际行为 |
| 小任务图谱让用户以为全景资产消失 | 认知迷失 | 保留全景/本轮施工切换，并显示当前图谱范围 |

## 8. 讨论结论

适合继续发展的方向是：为已有项目生成一份**有来源、有限范围、可审阅的项目现状基线档案**，并分别呈现工程结构图谱与候选功能基线图谱（双图谱分离）。它可以消除 Studio 的冷启动空白，并为第一张正向施工微合同提供背景。

但应避免把它描述成「历史施工合同」「已完成的施工状态」或「质量认证」。基线的价值在于让系统和用户对现状形成可追溯的共同参照；真正的改动授权、Scope 防护和质量结论仍须在每张正式微合同中独立建立，并由真实实现与证据支撑（确认 ≠ 授权）。
