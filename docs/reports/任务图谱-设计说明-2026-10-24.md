## 0. 结论摘要（先看这里）

| 问题 | 一句话答案 |
| --- | --- |
| **新建项目**能不能用图谱？ | **能。** 先把空目录变成受保护的 Git 工程（Alt-Flow A1），再开合同 → 聊需求 / 看假页面 → **确认原型** → 才有图。 |
| **导入的已有项目**能不能用图谱？ | **能。** 用 `stagent open <路径>`（或最近项目）打开同一工作台；图谱不区分「新仓 / 旧仓」，只认**当前这份合同有没有建过图**。 |
| 打开项目就自动有图吗？ | **不会。** 「打开 / 新建 / 导入」只是**进门**；图谱是进门之后、**确认原型**才落盘的施工计划图。 |
| 图上「排队中」是坏了吗？ | **不是。** 建图成功后节点一律全灰排队；要变绿必须真改文件 + 检查通过 + 指纹落盘（防假绿）。 |
| 今天 UI 能干什么？ | **全景/施工**切换（C.10q）；全景看合同摘要；施工侧看进度、建图、开工/核销（C.10n/o）；合入清树后自愈 Worktree（C.10p）。 |

**前提条件（两边一样）**

1. 本机已用 Daemon 打开该文件夹（`stagent open` / 最近项目；v0.1 尚无 Cursor 式系统选文件夹，见 D.1e 延后）。  
2. 工作区是 Git 仓（空目录会走 A1 初始化）。  
3. 左侧（或项目审阅）里有一份**可选中的合同**。  
4. 用户点过「确认原型并建图 / 确认原型并实施真实工程」——或历史上已落盘 `.stagent/specs/task_graph.json`。  
5. 看图时选中的合同，最好与磁盘上那张图的 `contract_id` 一致；否则会出现「磁盘有图、当前合同空态」的错觉。

## 1. 目的：老板要看见什么？为什么防假绿？

### 1.1 产品目的

Stagent 要把「AI 瞎改代码」变成**看得见的施工**：

- **拆清楚**：这一轮需求被拆成业务功能区 + 一串工程节点（任务 DAG）。  
- **看得见进度**：节点从灰（排队）→ 施工中 → 翠绿（点亮）。  
- **信得过**：绿灯不是模型口头说「做完了」，而是后台用**物理证据**核销。  
- **可验收 / 可质疑**：图与合同、假页面、真代码同一条旅程；觉得不对仍只跟右侧聊。

对非技术用户：你不需要懂 Git Worktree、Evidence、SHA；你只需要知道——**灰 = 还没做成；绿 = 真做成且检查过。**

### 1.2 防假绿（红线）

架构明确规定（§3.2.2 / ADR-009）：

- **禁止**模型或前端自己把节点标绿。  
- 点亮必须同时满足（COMMAND 模式典型口径）：  
  1. **受控写入**：目标文件真的写进任务工作区；  
  2. **验证退出码 0**：声明的检查命令跑通；  
  3. **指纹**：目标文件内容哈希（及绑定的提交指纹）由 Daemon **现场计算**，调用方不能自报。  
- 验证命令集合为空时，**禁止点亮**（`E_EMPTY_VERIFICATION_BLOCKED`），避免「空检查假绿」。

所以：图谱的目的不是「装饰进度条」，而是**施工透明度 + 验收门禁的可视化**。

## 2. 原理：从进门到点亮的一条链

```
打开/新建/导入项目（进门）
        │
        ▼
建立/选中「合同」（本轮授权说明书）
        │
        ▼
右侧聊需求 →（大事）假页面 Demo 试玩
        │
        ▼
【确认原型】→ Supervisor/前端拼「全灰提案」
        │
        ▼
Daemon 落盘 task_graph.json（节点全是「排队中」）
        │
        ▼
【开工下一节点】→ 节点变「执行中」（需要任务 Worktree）
        │
        ▼
Worker 真改文件（隔离工作区）
        │
        ▼
【核销点亮】→ Daemon 采证 + 校验 → 满足三证才变绿
        │
        ▼
全部点亮 / 双门禁通过 → 可合并；合并后 Worktree 常被清理
        │
        ▼
若图还在、树没了：开工/核销前自动重建树（C.10p），仍不假绿
```

### 2.1 进门 ≠ 有图

| 动作 | 作用 | 会不会直接出图谱？ |
| --- | --- | --- |
| 新建空项目 / A1 初始化 | `git init`、建 `.stagent/` | 否 |
| 导入已有仓库（`stagent open`） | 绑定工作区、起 Daemon、开工作台 | 否（除非该仓以前已确认过原型、磁盘上已有图） |
| 最近项目一键重开 | 带钥匙回到同一工作台 | 否（同上：有历史图才显示） |
| 聊需求 / 出草案 / 出合同 | 准备「这一轮做什么」 | 否 |
| **确认原型并建图** | 真正创建全灰 Task Graph | **是** |

对照文档：`docs/reports/打开项目-愿景与现状.md`——「打开项目是进门，八步旅程是进门之后」。

### 2.2 建图时发生了什么（S.6）

用户点确认后：

1. 前端用当前选中合同调用 `buildProposalFromContract`（确定性、保守拆解）：  
   - 一个功能区 ≈ 合同标题；  
   - 每个可写路径（或验收条目）≈ 一个「落实：…」节点；  
   - 节点串成依赖链；验证命令用合同里已有别名，否则占位 `verify`（空集仍会被挡住，不会假绿）。  
2. `POST /api/graph/proposal` → Daemon `createFromProposal`：节点**一律 PENDING（排队）**，写入 `.stagent/specs/task_graph.json`。  
3. 中栏切到「任务图谱」视口；广播 `TASK_GRAPH_UPDATED`。

**重要**：建图 ≠ 开工。建图只是「计划书全灰上墙」。

### 2.3 排队 → 开工 → 点亮（C.7 + C.10o + C.10p）

| 老板看见 | 后台含义 |
| --- | --- |
| 排队中 | `PENDING`：等前置点亮且尚未开工 |
| 执行中 | `RUNNING`：已 `start`，等待真实施工与核销 |
| 已点亮 | `ILLUMINATED`：三证通过 |
| 失败 / 阻断 / 待重验 等 | 七态中其余状态；外部手改代码会变「待重验」并可能连合同一起降级 |

UI（C.10o）把按钮接到既有 API：

- 开工 → `POST /api/graph/nodes/start`  
- 核销 → `POST /api/graph/verify`（文件哈希 / Scope / HEAD 由 Daemon 现算，**前端伪造无效**）

C.10p：若合同曾合并、任务树被清掉，再点开工/核销会先 **ensure/重建** `.stagent/worktrees/task-<contract_id>`，避免只报「Worktree 不存在」；**重建树不会自动点亮**。

## 3. 适用边界

### 3.1 哪些项目可以用？

| 项目类型 | 能否用图谱 | 说明 |
| --- | --- | --- |
| 新建空目录 | 能 | 先 A1 初始化，再走合同 → 确认原型 |
| 导入已有 Git 工程 | 能 | 同一套引擎；节点常按合同可写路径拆出「落实：某文件」 |
| 非 Git / 未 open | 不能正常用 | 需先初始化或 `stagent open` |
| 任意语言巨型单体 | 有限 | v0.1 官方基线偏 TS/JS；验证命令缺失时可能降级为人工点亮模式（规范矩阵） |

### 3.2 哪些合同状态「有图 / 能操作」？

| 情况 | 图谱页表现 |
| --- | --- |
| 从未确认原型 | 空态：「当前合同还没有图」+ 建图按钮（C.10n） |
| 已建图，未开工 | 有图，节点多「排队中」；可开工 |
| 施工中 | 部分执行中 / 已点亮 |
| 合同已 **MERGED**，图仍在磁盘 | 仍可打开看；再核销需 C.10p 重建 Worktree；**不会因为重建就变绿** |
| 磁盘图挂在合同 A，UI 选中合同 B | 易表现为空态或对不上——请先点左侧与图一致的那份合同 |
| 用户放弃本轮（A4） | 工作区清理；图/合同按中止流程归档，不应假装还在施工 |

### 3.3 与保护清单、隔离施工的关系（P.1 / W.5a）

- **保护清单**：登录/支付等锁区与图谱正交——碰锁先问老板；图谱点亮仍只认证据。  
- **Worktree / Worker 隔离**：真改代码在任务树里进行，主分支保持干净；合并后门禁与 Trailer 审计另走控制面，不由图上「点一下变绿」替代。

## 4. 与 UI 入口的关系

### 4.1 日常入口（C.10c 后）

- **主路径**：合同操作台内的「任务图谱」视口（单门）。  
- 左栏图谱入口：打开/聚焦合同操作台并切到该视口，**不再**另开一套独立「任务图谱系统 Tab」当日常双入口。

### 4.2 无图 vs 有图（C.10n → C.10o）

| | 无图 | 有图 |
| --- | --- | --- |
| 顶栏「业务功能导图 / 执行拓扑」 | 禁用（避免像没反应） | 可切换两种看法 |
| 刷新 | 有「刷新中…」反馈 | 重新拉 Daemon 快照 |
| 主按钮 | 「确认原型并建图」 | 「开工下一节点」「核销点亮」 |
| 点节点 | — | 看详情；可对可开工/可核销节点操作 |
| 失败 | 黄条在图谱顶栏（含建图失败） | 黄条说明为何没点亮 / Worktree 等 |

### 4.3 施工侧两种看法（C.10q 改名后）

1. **本轮施工·功能汇总**（原名「业务功能导图」，易与进门全仓脑图撞名）：按**本轮**功能区汇总下属工程节点真实状态（点亮只认证据）。  
2. **执行拓扑**：看节点依赖与排队/施工顺序。

> 进门「项目功能清单 / 业务功能脑图」属**全景**，见下方 §9；不要和施工汇总混叫。

## 5. 关键数据与路径（维护用，正文仍尽量白话）

### 5.1 磁盘权威文件

| 路径 | 含义 |
| --- | --- |
| `.stagent/specs/task_graph.json` | 任务图权威落盘（Daemon 独占写） |
| `.stagent/contracts/<contract_id>.json` | 合同快照 |
| `.stagent/worktrees/task-<contract_id>/` | 本轮任务隔离工作区 |
| `.stagent/protection.json` | 保护清单（P.1） |
| `~/.stagent/recent-projects.json` | 本机最近项目（非业务仓内） |

常量：`TASK_GRAPH_RELATIVE_PATH = ".stagent/specs/task_graph.json"`（`src/lib/graph/task-graph.ts`）。

### 5.2 图快照主要字段（示意）

- `schema_version` / `graph_id` / `contract_id` / `revision`（单调递增）  
- `functional_tree[]`：业务功能区  
- `nodes[]`：`node_id`、`title`、`state`（七态）、`depends_on`、`target_files`、`verification_mode` / `verification_commands`…  
- `fingerprints` / `progress` / `issues`  
- `generated_at` / `updated_at`

前端**禁止**直接读盘当权威；统一经 Daemon HTTP/WS 快照（`GET /api/graph`、`TASK_GRAPH_UPDATED`）。

### 5.3 HTTP API（Daemon）

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/graph?contract_id=` | 读快照；可按合同过滤 |
| POST | `/api/graph/proposal` | 提案建图（全 PENDING） |
| POST | `/api/graph/nodes/start` | 开工一节点（前先 ensure Worktree） |
| POST | `/api/graph/verify` | 核销点亮（Daemon 现算证据） |
| POST | `/api/graph/stale` | 外部改码 → 节点待重验 + 合同降级 |

客户端封装：`src/lib/daemon-api.ts`（`createTaskGraph` / `startTaskGraphNode` / `verifyTaskGraphNode`…）。

### 5.4 核心模块

| 模块 | 职责 |
| --- | --- |
| `daemon/graph/graph-engine.ts` | 内存权威、装载/落盘、start、状态机 |
| `daemon/graph/illumination-verifier.ts` | 三证判定；空集拦截 |
| `daemon/graph/evidence-collector.ts` | 文件哈希 / Scope / HEAD 现算 |
| `src/lib/journey/proposal-from-contract.ts` | 合同 → 全灰提案 |
| `src/components/graph/TaskGraphPanel.tsx` | 图谱 UI（空态 / 开工核销） |
| `src/lib/graph/startable.ts` | 谁可开工（依赖已点亮） |

### 5.5 节点七态（老板文案）

| 状态 | 白话 |
| --- | --- |
| PENDING | 排队中 |
| RUNNING | 执行中 |
| ILLUMINATED | 已点亮 |
| FAILED | 失败 |
| REPAIRING | 返工中 |
| BLOCKED | 已阻断 |
| STALE_REVERIFY | 待重验 |

## 6. 已知限制与后续可立卡项

### 6.1 已知限制（诚实边界）

1. **建图拆解仍偏保守**：主要按可写路径/验收条生成「落实：文件」节点，还不是完整智能功能树产品形态。  
2. **核销与真施工员尚未完全「一键无人值守」**：C.10o 提供开工/核销入口；日常项目级 Worker 适配与「看着代码长出来自动点亮」仍有体验缺口（见非技术旅程验收稿）。  
3. **COMMAND 核销**：UI 可按声明别名提交退出码；**写入与指纹仍由 Daemon 现算**——没有真文件变化时不会假绿。  
4. **打开项目 UX**：真·系统文件夹选择器（Import/New 同壳）在 **D.1e → v0.2+**。  
5. **图与合同一对多心智**：工作区当前权威图通常挂一份 `contract_id`；切换合同时要注意是否同一张图。  
6. **MERGED 后再施工**：可重建 Worktree，但是否业务上允许「合并后再点亮旧图」属于产品策略，需避免误导为「还能改已合并主线」而不走新合同。

### 6.2 后续可立卡方向（仅建议，未授权不开工）

| 建议方向 | 价值 |
| --- | --- |
| 切换合同时自动对齐/提示图所属合同 | 减少「有图却空态」错觉 |
| 确认原型后可选「自动开工下一节点」 | 少一次点击（仍不假绿） |
| Worker 完成写入后自动触发 verify | 更接近「看着变绿」 |
| 节点详情补 Diff 摘要 / 测试报告抽屉 | C.7 残余口径 |
| 合并后旧图只读归档 vs 强制新合同重建 | 产品策略收口 |
| 更聪明的功能树拆解（Supervisor 提案质量） | 少「落实：路径」机械感 |
| **C.10q 双视角壳（本轮）** | 全景/施工切换 + 改名消歧义 |
| **v0.2 三张真全景图** | 进门脑图 / 旅程 / 概念（RFC 附录 C） |

## 8. 给 Tina 的三句话版

1. **新建和导入的项目都能用图谱**——先打开项目、有合同，再「确认原型」；图谱不挑新仓旧仓。  
2. **图谱是施工计划墙**：先全灰排队，绿灯必须真改文件并检查过，防止 AI 口头报喜。  
3. **今天可以在图谱上建图、开工、核销**；合并后任务树没了会自动补树，但仍然不会无证据变绿。

## 9. 四张「透视卡」与 Studio 双视角（方案总表）

> Tina 定稿（t683u）：非专业用户面对软件只有四个根本问题；用四张渐进式透视卡回答。  
> **防假绿纪律不变**：全景只解释「是什么 / 怎么用 / 管什么」；**绿只能来自施工核销**。

### 9.1 四张透视卡

| # | 层 | 回答的问题 | 图表 | v0.1 现状 | v0.2 |
| --- | --- | --- | --- | --- | --- |
| 1 | 结构层 | 这个软件能干嘛？ | **业务功能脑图**（白话，禁技术词） | **没有**真脑图；全景仅合同摘要 + 占位卡「项目功能清单」 | 进门基于全仓/README/requirements **自动总结** |
| 2 | 行为层 | 用户怎么流转？ | **用户旅程泳道**（大白话，非时序图） | **没有**（占位卡） | 点某主线时展开 3~5 步泳道 |
| 3 | 资产层 | 存了什么东西？ | **业务概念图**（谁拥有谁，无字段细节） | **没有**（占位卡） | 按需查看领域关系 |
| 4 | 施工层 | 这轮要改哪几块？ | **任务图谱**（灰→绿硬核核销） | **已有**（C.7 + S.6 + C.10n/o/p） | 继续增强拆解/自动核销体验，不改三证 |

### 9.2 场景表：哪张图何时给谁看？

| 图表 | 核心疑问 | 谁来看 | 何时出现 | 形式 |
| --- | --- | --- | --- | --- |
| 业务功能脑图 | 项目有什么功能？ | 老板 / 业务方 | 一打开项目就看（进门即有） | 白话树状脑图，可展开 |
| 用户旅程 | 用户从头到尾怎么用？ | 运营 / 产品 | 了解某条主线时 | 极简泳道，无底层函数 |
| 业务概念卡 | 管了哪些业务资产？ | 决策 / 审计 | 按需看数据资产 | 方块 + 关系线 |
| 任务施工图 | 这轮改动做得怎样？ | 验收人 / 负责人 | **确认原型后**施工时 | DAG，灰变绿硬核核销 |

### 9.3 Studio 双视角落地（v0.1 = C.10q）

中栏合同操作台内，原「任务图谱」视口升级为：

1. **视角 A · 全景（平时看）**  
   - 未确认原型 / 无图：默认全景。  
   - 展示：合同 intent 白话摘要（标题/描述/验收/需求提示）+ 三张 v0.2 占位卡。  
   - **禁止**全景节点显示施工绿灯。  
2. **视角 B · 施工（改代码时看）**  
   - 确认原型建图成功后：自动（或一切换）到施工 = 既有 Task Graph。  
   - 顶栏内仍是「本轮施工·功能汇总 / 执行拓扑 / 开工 / 核销」。  

切换壳：`StudioLensShell`（`全景` | `施工`）；路由：`resolveDefaultLens` / `resolveActiveLens`（无图→全景，有图→施工，无→有强制施工）。

### 9.4 与现有任务图谱的关系（消歧义）

| 名称 | 是什么 | 不是什么 |
| --- | --- | --- |
| **项目功能清单**（全景） | 进门看「能干嘛」的摘要入口 | 不是本轮点亮进度 |
| **业务功能脑图**（v0.2） | 全仓白话能力树 | 不是 Task Graph 的 functional_tree |
| **本轮施工·功能汇总** | 本轮 DAG 上层汇总，点亮认证据 | 不是进门全仓脑图（旧称「业务功能导图」易撞名，已改） |
| **执行拓扑** | 本轮节点依赖与排队顺序 | 不是用户旅程泳道 |
| **任务图谱 / 施工视角** | 确认原型后的计划墙 + 开工核销 | 不是打开项目就自动全绿 |

### 9.6 防假绿（再次强调）

- 全景**不得**绑定 `ILLUMINATED` / 进度百分比冒充「功能已做成」。  
- 施工点亮仍只认：受控写入 + 验证退出码 0 + Daemon 现算指纹。  
- C.10q **不改** illumination / start / verify / C.10o / C.10p。
