## 1. 目的与适用范围

本章规定 Stagent 如何识别、创建、审阅、冻结、验证、归档或撤销交付过程中产生的文档资产，并规定需求断言快照与合同、代码基线、验证证据及 Git Commit 之间的可审计关联。

本章适用于至少以下资产：

- 用户意图与需求澄清记录；
- 需求规格及可验证断言快照；
- 白话合同及其结构化授权内容；
- 实施任务图谱、验收计划与测试引用；
- ADR（架构决策记录）及相关设计说明；
- 验收报告、测试结果、Evidence 与发布记录。

Mock Demo、截图或设计参考可作为意图对齐证据，但除非合同明确纳入交付资产，不自动成为项目源码、授权范围或验收通过的依据。

## 2. 基本原则

1. **文档是受治理的交付资产，不是对当前代码事实的替代。** 文档结论必须与可核验的代码、配置、测试结果和仓库状态区分；发现不一致时不得用文档覆盖事实。
2. **授权必须有明确来源。** ADR 记录决策理由，不授予写入权限、不扩大合同 Scope，也不替代用户签署、策略校验或执行凭证。
3. **签署冻结的是本轮已确认的意图与授权边界。** 冻结后的需求变化不得静默覆盖原快照，必须产生新版本并重新评估授权及受影响验证。
4. **验证结论必须指向确定的候选代码与需求版本。** 代码、需求断言或验证配置变化后，受影响的 Evidence 必须失效或重新评估；旧证据不得为新候选背书。
5. **历史记录可追溯，不等于仍然有效。** 归档用于保留历史；撤销用于标识不再适用或被取代的资产。二者均不得被当作当前授权。
6. **不能以状态名称冒充实现能力。** 若当前系统无法提供不可变存储、完整哈希校验或可靠 Git 事实读取，必须明确标记为未实现/未验证，不得宣称资产已被安全冻结或证据已绑定。

## 3. 资产元数据与状态定义

每个受治理资产应有稳定标识及版本，并在可行时记录以下元数据：

- `asset_id`、`asset_type`、`version`、`status`；
- 创建者/来源、创建时间、变更说明；
- 所属项目、会话、合同与任务（如适用）；
- 内容摘要算法与摘要值；
- 关联的需求快照、代码基线、候选版本及 Evidence；
- 当前版本的权威存储位置及访问策略。

### 3.1 两轨状态（强制分轨 · 对齐 EO-01）

| 轨 | 类型名 | 管什么 | 权威来源 |
|---|---|---|---|
| **A. 文档资产态** | `DocumentAssetStatus` | 单份文档/快照文件自身的起草→冻结→核验→归档 | **本文** |
| **B. 交付主生命周期** | `DeliveryLifecycleState` / EO-01 `DeliveryState` | 用户可见本轮进度（方案→Demo→签署→施工→验收→合并→归档） | 右栏 **§14.11 EO-01**；广播叠 `session_epoch`+`state_seq`（澄清 **§6** / Checklist **§3** Top5 #2） |
| **C. 子任务活动态** | `TaskSubState` | `DEMO_BUILDING` / `CONTRACT_SIGNING` / `MERGING` 等瞬态 | 右栏 §14.2 / EO-01；**不得**与 A/B 揉成一张扁平表 |

**旧名 → 新名（交付叙事）**：

| 旧写法（deprecated） | 新写法（CLOSED） | 说明 |
|---|---|---|
| 以资产 `FROZEN` / `APPROVED` 充当「已签署可开工」主交付态 | `CONTRACT_SIGNED` | 签署瞬间：资产轨仍可记 `FROZEN`（快照不可静默改写）；**交付主态**必须是 EO-01 |
| 笼统 `VERIFIED`（交付已完结） | `CANDIDATE_VERIFIED` → `MERGED` → `DELIVERED` | 合并前候选核验 ≠ 已合并 ≠ 脱敏归档完结；**禁止** `MERGED → REWORK_REQUIRED` |
| 单一 `DEMO_READY` 无模式 | `DEMO_INTERACTIVE_READY` / `DEMO_NATIVE_FLOW_READY` / `DEMO_DEGRADED_READY`（或 `DEMO_READY`+`demo_mode`） | 对齐 EO-01 / EO-06；`PLAN_CONFIRMED` 后才进 Demo，DAG 单向不可跳步 |
| 资产路径含糊 / 与施工区混用 | `.stagent/drafts/` · `prototypes/` · `records/{contract_id}/` · `worktrees/{contract_id}/` | **EO-02**；Worker **只**挂本 worktree，禁 `../` |

### 3.2 文档资产状态（`DocumentAssetStatus`）

资产状态为（**仅**描述文档文件，**不是** DeliveryState）：

| 状态 | 含义 | 可否作为本轮执行或验收依据 |
|---|---|---|
| `DRAFT` | 正在整理的工作稿，内容尚未完成澄清或审阅。 | 否 |
| `PROPOSED` | 已提交供用户或有权审阅者确认的提案版本。 | 否；只能作为待批准提案 |
| `FROZEN` | 已按规定完成确认/授权，内容摘要固定，并与本轮合同或批准记录关联。 | 是，但仅限明确授权的范围与生命周期；**对应交付主态推进至 `CONTRACT_SIGNED` 的冻结瞬间**，本身不是 DeliveryState |
| `VERIFIED`（资产轨） | 针对指定代码候选与验证配置完成核验，且所需断言均有有效证据支持。 | 是；只对被绑定的候选版本有效。**交付主态**此时应对齐 **`CANDIDATE_VERIFIED`**（尚未合并）；合并成功 → `MERGED`；脱敏归档成功 → `DELIVERED`。资产轨可再 `ARCHIVED` |
| `ARCHIVED` | 已结束当前用途并保留为历史记录。 | 否；只供追溯；常与交付 `DELIVERED` 后的 records 归档同拍 |
| `REVOKED` | 已被明确撤销、作废或替代；需记录原因及替代关系。 | 否 |

资产 `FROZEN` 表示内容及授权基线不可被静默改写，不表示功能已通过验证。资产 `VERIFIED` 表示指定验证已完成，不表示对其他候选版本、运行环境或未覆盖质量属性作出保证，也**不**表示已 `MERGED` / `DELIVERED`。

## 4. 状态转换规则

### 4.1 允许的主要转换

```text
DRAFT -> PROPOSED -> FROZEN -> VERIFIED -> ARCHIVED
  |          |          |          |
  +----------+----------+----------+-> REVOKED

DRAFT -> ARCHIVED       （明确放弃的草稿）
PROPOSED -> DRAFT        （退回修改；生成新版本或可追溯修订）
FROZEN -> FROZEN         （同一冻结版本只读；变更必须生成新版本）
VERIFIED -> FROZEN       （仅限验证结论被撤销或失效；保留原验证记录）
```

图示仅表达允许的概念转换。实现时不得通过直接改写历史记录来模拟转换；每次状态变化须产生可审计的事件或等价记录。

### 4.2 转换门槛

- **`DRAFT -> PROPOSED`**：必需字段齐全；来源与未决项已标注；需求断言可读且尽量可验证；影响范围和假设不确定之处明确披露。
- **`PROPOSED -> FROZEN`**：有权用户/审批者对明确版本作出显式确认；授权范围、拒绝范围、验收条件及相关合同均已记录；为规范化内容计算摘要并保存冻结记录。沉默、预览或口头上对某个局部方向表示认可，均不自动等同于签署整个合同。
- **`FROZEN -> VERIFIED`（资产轨）**：全部必需断言均有与指定候选代码版本匹配的有效证据；必需测试集非空；失败、跳过、未覆盖项和人工验收结论如实记录；没有尚未处理的阻断项。证据不充分时维持 `FROZEN` 或标记验证失败，不得点亮为已验证。**同步**：交付主态进入 **`CANDIDATE_VERIFIED`**（合并前）；**不得**在未合并时宣称 `MERGED`/`DELIVERED`。
- **`VERIFIED -> ARCHIVED`（资产轨）**：本轮交付关闭或被新版本取代；归档记录指向最终验证版本、验收结论和后续资产。**同步**：Git 合并成功标定 **`MERGED`**；脱敏三件套写入 `.stagent/records/{contract_id}/` 且审计哈希成功后才 **`DELIVERED`**（EO-05；任一步失败停 `MERGED`，严禁伪造完结）。
- **任一非终态 -> `REVOKED`**：撤销人、时间、原因、影响范围及替代版本（如有）可追溯；撤销不得删除既有签署和验证历史。

### 4.3 终态及修订

`ARCHIVED` 与 `REVOKED` 是只读历史状态。需要继续使用时，应从历史内容派生新的 `DRAFT` 或 `PROPOSED` 版本，并保留来源链接，不得将终态资产原地恢复成有效状态。

对 `FROZEN` 或 `VERIFIED` 内容的任何实质修改都必须产生新版本。若变化影响用户意图、授权范围、验收条件、代码影响面或安全策略，应重新进入澄清/合同审批；仅格式性调整是否允许不触发重新授权，须由规范化与内容差异策略明确定义，且不得改变语义摘要所覆盖的内容。

## 5. 全生命周期职责边界

| 阶段 | 责任边界 | 文档资产操作与输出 |
|---|---|---|
| 澄清前 | Supervisor/分析组件可读取其获准访问的项目资料与仓库事实；不得把旧文档未经核验地当作当前事实。 | 记录来源、版本、工作树与基线事实（能力可用时）；标明冲突、过期内容和未知项。 |
| 需求澄清 | 用户决定业务意图与关键取舍；Supervisor 负责提问、整理和提出建议；任何组件均不得把建议伪装成用户决定。 | 创建需求快照、断言草案、Demo 参考及合同提案；未签署前均为 `DRAFT`/`PROPOSED`，不得授权真实项目写入。 |
| 授权冻结 | 用户对明确的合同/需求版本显式授权；Daemon 或等价可信控制面记录批准并校验完整性。 | 资产轨：冻结需求快照与合同版本为 `FROZEN`；交付主态 → **`CONTRACT_SIGNED`**（EO-01）。记录摘要、批准主体和时间、基线标识、授权 Scope、策略版本及适用期限；签署期 GC 白名单见 EO-05。 |
| 实施 | 实施 Agent 只能在有效合同和凭证允许的范围内工作；不得静默改写冻结需求、授权范围或历史 ADR。Worker **只**挂载 `.stagent/worktrees/{contract_id}/`（**EO-02**），禁 `../` 与符号链接穿出；`prototypes/`/`records/` 不进沙盒。 | 可产生实施记录、测试引用、ADR 提案和实现说明；需修改受控文档时，先检查是否在获准路径/操作内，必要时生成待审版本。交付主态：`IMPLEMENTING` / `PAUSED`（软停见 EO-07 / Top5 #3）。 |
| 验收 | 验收者依据冻结断言和实际候选版本判断；Supervisor 可提出质疑或汇总证据，但不能伪造通过结论。 | 将每项断言关联到候选代码版本、证据和结果；通过后资产轨可标 `VERIFIED`，**交付主态**标 **`CANDIDATE_VERIFIED`**；失败项保持未通过并记录原因。合并前质疑成立 → `REWORK_REQUIRED`（不得倒流已 `MERGED`）。 |
| 合并/关闭 | 有权人员或已批准的自动化策略执行合并；文档治理不得替代合并授权。 | 候选与实际合并 Commit 关联 → 交付主态 **`MERGED`**；脱敏归档入 `records/{contract_id}/`（含 `audit-manifest.json`，Top5 #5）成功后 → **`DELIVERED`**；资产轨可 `ARCHIVED`。保留被取代版本和差异。 |

## 6. 需求断言快照

### 6.1 快照内容

需求断言快照是本轮“用户希望交付什么、如何判断”的受控版本，不是任意聊天记录的全文替代品。至少应包含：

- 需求快照标识、版本、来源会话和生成时间；
- 用户明确确认的目标、用户旅程/关键交互和业务规则；
- 可观察的验收断言；每项断言具备唯一 `assertion_id`、预期结果和适用条件；
- 已确认决策、明确排除项、未决问题、假设及风险；
- 对应合同条款、授权 Scope、任务节点和验证方法的引用；
- 对设计参考、Mock Demo、样例数据等材料的引用与用途说明；
- 人工验收项与机器验证项的区分。

不得把模型推断的默认值写成用户决定。无法在编码前确定的细节应作为显式假设、开放项或后续小合同处理，并由授权流程决定其是否阻断实施。

### 6.2 断言质量与核销

每条断言应尽可能明确、可观察、可复现，并标注至少一种核验方法。断言可关联多个证据，但“有测试文件”不等于“断言已通过”；证据必须显示实际执行结果并对应当前候选版本。

验收矩阵至少包含：`assertion_id`、断言文本/版本、验证方式、Evidence 标识、候选版本标识、结果（通过/失败/跳过/未验证）、执行时间及例外说明。必需断言不得因缺少证据、空测试集或跳过而自动视为通过。

## 7. 冻结、哈希与 Git Commit 绑定

### 7.1 授权冻结时的绑定

显式签署时，应对规范化后的合同和需求快照分别计算内容摘要，并生成可审计的冻结记录。记录至少关联：

- `project_id`、`session_id`、`contract_id`；
- `requirements_snapshot_id`、版本与内容摘要；
- `contract_version` 与合同内容摘要；
- 授权主体、批准时间及批准动作；
- 代码基线标识：仓库标识、基线 Commit SHA（若可获得）、基线工作树状态/差异摘要（若适用）；
- Scope、允许/禁止操作、适用策略版本及凭证标识；
- 需求断言、验收集与任务图谱版本摘要。

冻结记录必须反映真实读取到的仓库状态。若基线 SHA 缺失、仓库状态无法读取或存在未处理的工作树改动，应明确标记并按策略暂停或限制执行；不得虚构 SHA、干净工作树或基线一致性。

### 7.2 候选版本与 Evidence 绑定

实施过程中，每个验收候选必须具备可识别的代码内容指纹。优先记录 Git tree/object 标识或等价的完整内容摘要；同时记录实际候选 Commit SHA（若已经提交）。Evidence 至少绑定：

- 需求快照摘要及相关 `assertion_id`；
- 合同摘要与授权 Scope；
- 候选代码 tree/content fingerprint，及候选 Commit SHA（如存在）；
- 测试/验证配置版本、命令或方法、执行环境、执行时间和原始结果引用；
- Evidence 创建方、完整性校验信息及状态。

候选代码变化后，必须重新计算其指纹。若变化触及被验证断言、其依赖、配置或验证环境，则相关 Evidence 标为失效/过期并重新运行；影响无法确定时，按受影响处理，不得沿用旧通过结果。

### 7.3 合并 Commit 的最终关联

Git Commit SHA 只有在 Commit 实际创建后才可记录。验收通过后，应将通过验收的候选指纹与实际合并 Commit SHA 关联，并确认合并后的 tree 与被验证候选一致；若合并冲突解决或其他变化导致 tree 不同，必须对变化影响进行评估并重跑受影响验证。

最终交付记录应至少形成如下关联链：

```text
用户批准记录
  -> 冻结合同摘要 + 冻结需求快照摘要
  -> 基线 Commit / 基线状态
  -> 授权 Scope 与任务版本
  -> 候选 tree/content fingerprint + Evidence
  -> 实际合并 Commit SHA + 最终 tree 校验
  -> 归档的验收结果与文档版本
```

此关联可由 Git 提交说明/Trailer、版本化侧车清单、受控数据库记录或其组合实现。**无 Git 时**权威侧车定为 `.stagent/records/{contract_id}/audit-manifest.json`（澄清 **§6** Top5 #5 / EO-03·04·05）：脱敏管道后落盘快照与审计事件哈希，**独立于** Git Trailer 证明完整性。无论选择何种方式，均须可审计、防静默改写，并能从 Commit 或项目交付记录定位到对应的授权和验证链。Git 提交信息本身不能替代签署记录、访问控制或独立完整性校验。交付主态须走 **`CANDIDATE_VERIFIED` → `MERGED` → `DELIVERED`**，不得用资产 `VERIFIED`/`ARCHIVED` 跳步冒充。

## 8. 需求变更、基线漂移与证据失效

1. **需求或合同变化**：冻结后出现新业务规则、扩大 Scope、改变交互/验收标准或新增权限时，旧合同不自动覆盖；建立新提案版本，按风险重新审批，并重新评估任务图谱和验证集合。
2. **实现计划变化但不改变授权**：可在合同允许范围内更新实施说明或任务安排；若改变可写路径、允许命令、风险边界或验收承诺，必须重新授权。
3. **代码基线漂移**：若 main/目标分支或工作树相对于冻结基线发生变化，暂停受影响执行或按明确策略重新基线化；旧验证证据不因此自动适用于新基线。重新基线化不得改变用户已批准的需求和 Scope。
4. **候选版本变化**：变化后的代码是新候选；依据差异与依赖关系失效相关 Evidence。无法可靠判定影响时，采取保守策略并重新验证。
5. **文档与代码事实冲突**：记录冲突、来源和处置决定；未经验证不得把设计目标改写为“已实现”。影响授权或验收的冲突必须在继续前解决或由有权者明确接受例外。
6. **撤销**：合同撤销、授权过期、凭证失效或安全事件发生时，按执行控制规范停止后续操作并撤销相关资产的有效性；已产生的副作用、外部系统变更或未保存内容不得被假定为自动回滚。

## 9. 审计与一致性检查

系统及人工治理流程应能够回答：

- 谁确认了哪一版需求和合同，确认内容的摘要是什么？
- 该轮工作基于哪个仓库、基线和实际工作树状态？
- 哪些文件/操作获准，凭证何时生效或撤销？
- 每条必需断言由什么证据核验，证据针对哪个候选内容指纹？
- 最终合并 Commit 与通过验证的候选是否一致？若不一致，执行了哪些补充验证？
- 哪些文档被修改、审核、冻结、验证、归档或撤销，修改的责任主体和原因是什么？

审计记录应保留失败、拒绝、重试、过期、冲突和人工例外；不得只保留成功路径。若某项问题无法回答，应将相应资产或交付状态标记为未验证，而非推断为合规。

## 10. 待补充的实现决策

本章确定治理语义，不预先指定尚未定型的技术实现。正式实施前至少需定义：

1. **规范化与哈希算法**：文档如何规范化、使用何种摘要算法、如何处理附件/二进制设计资产及版本升级。
2. **权威存储与不可变审计**：冻结记录、签署事件、Evidence 和撤销记录存放位置、访问控制、保留期限及恢复策略。
3. **状态机 API/事件 Schema**：状态转换的主体、前置条件、幂等键、并发冲突、失败重试与事件顺序。**命名已 CLOSED**：交付主态 = EO-01 `DeliveryState`；资产态 = 本文 `DocumentAssetStatus`；广播须带 `session_epoch`+`state_seq`（Top5 #2）。字段级事件体仍可立卡细化，**不得**再开「要不要分轨 / 要不要废除笼统 VERIFIED」选择题。
4. **Git 关联格式**：基线、候选、合并 Commit 的字段结构；Trailer 细节可立卡。**无 Git 降级路径已 CLOSED**：`records/{contract_id}/audit-manifest.json`（Top5 #5）；废止旧建议路径 `.stagent/metadata/`。
5. **变更影响与 Evidence 失效规则**：如何判定需求、代码、测试配置和依赖变更影响哪些断言；不确定时的保守处理。
6. **用户确认与人工例外**：不同资产的签署粒度、授权人角色、二次审批条件、撤销权限及例外记录格式。
7. **文档写入授权**：哪些规范/任务/ADR 可在合同内更新，受保护资产如何审核，自动生成文档的审阅责任如何划分。
