## 0. 给 Tina 的一页纸

| 问题 | 白话答案 |
| --- | --- |
| **本文在写什么？** | **不是空概念。** 写的是「本轮可交付改动」如何用运行时合同高质量履约：意图写清、围栏关住、验收跑真、状态机合法。质量靠小步合同叠出来，不是一次出顶级大系统。 |
| **合同是什么？** | 本轮「改代码」的**授权说明书 / 施工护照**：写清要做什么、准改哪些文件、不准碰什么、怎么检查、谁批过。机读小卡 JSON，不是几十页 Markdown。 |
| **目标是什么？** | 让 AI **只能在你划定的安全围栏里施工**；改老项目时尤其要挡住登录/支付等地基；做完要留下可核销的证据，而不是口头报喜。 |
| **原理是什么？** | **意图与授权分离**：聊需求 / 玩假页面 ≠ 批准动手；动手前必须有一份可校验的合同（或 Fast Path 系统自动签发的轻量合同）。升版必重批。聊天记录**不整段**拿去拆任务；进拆解的是合同；确认原型后落灰图；绿灯靠三证。 |
| **什么时候需要？** | **本轮要改代码（施工）时必须有。** 刚导入项目看【项目全景】勘察家底时，产品叙事上**不需要**合同（真·全仓三卡属 v0.2；v0.1 全景仍是摘要占位）。见 §4 与任务图谱 §9.9。 |
| **和两份大规范什么关系？** | 大规范 = 造 Stagent 的「宪法」；运行时合同 = 用户每次需求的「施工护照」。见 §0.1。 |
| **和「静默合同」是一回事吗？** | **不是。** 正式软件合同 = 审批 + Scope + 证据 + 可合并；静默合同 = 自由模式下后台记一笔「这轮打算改哪」，前端无感，**不能当合并依据**。 |

### 0.1 宪法 vs 施工护照（别把两类「合同」混了）

| 维度 | 《架构规范》+《任务规范》（宏观规范） | Stagent 运行时合同（本文主角） |
| --- | --- | --- |
| 形式 | 几十页 Markdown 中文大文档 | 几百行级结构化 JSON（`.stagent/contracts/<id>.json`） |
| 范围 | 造 Stagent 本身：模块、终极形态、任务排期 | **仅本轮**具体改动（如「加退款按钮」） |
| 读者 | 人 / 架构师 / 派发 Agent 的执行纪律 | 机器：Gateway、状态机、命令拦截、核销 |
| 生命周期 | 长期维护、跨月演化 | 临时：确认原型建图 → 验过 → 合并入主干后归档 |
| 比喻 | **国家宪法 / 城市规划** | **本轮施工许可证 / 单次护照** |

**关系一句话**：你用大规范 + 四件套（typecheck / 测试 / 证据 / 合入）人工「养」出 Stagent；产品把同一套纪律自动化成用户每次需求的小张机读护照。用户**不必**亲自写几十页文档——条文由 Supervisor 起草、Gateway 执行。

### 0.2 聊天 → 合同 → 灰图 → 绿灯（链路心智）

```
右侧白话对话（澄清意图）
        │  不整段聊天记录拿去拆施工任务
        ▼
Supervisor 提纯 → 合同草案（意图 + 围栏 + 验收）
        │
        ▼
你确认原型 / 批准
        │
        ▼
按**合同**确定性落全灰任务图（施工视角）
        │
        ▼
Worktree 真改文件 + 验证退出码 0 + 指纹
        │
        ▼
三证齐全 → 节点点亮（绿灯）；合同本身不发绿灯
```

闲聊、玩 Demo、看全景：**都不自动等于**已批准施工。只有合同（或 Fast Path 轻量合同）过闸后，才进入可交付改动链路。

### 0.3 能力边界（诚实）

| 能做到 | 做不到 / 尚未做到 |
| --- | --- |
| 叠出**可控、可验收的增量改动**；改老项目时围栏护地基 | **不等于**一次对话自动长出顶级大系统 |
| 范围围栏 + 证据点亮 + 非技术人看得见进度 | 自动拆解仍偏机械；复杂架构仍要人拍板 |
| 与全景严格解耦：摸家底不需合同 | 真·进门全景三卡属 **v0.2**；v0.1 全景多为摘要占位 |

底盘稳来自纪律，不是模型一次写完。开发 Stagent 时的人工规范 + 四件套证明这套有效；产品侧要把「更聪明拆解 / 进门全景 / 质量上限」继续装进盒子——**安全下限已立，高质量上限仍在补**，见 §7 / §7.3。

## 1. 目标（Why）

### 1.1 产品目标

0. **高质量可交付的本轮改动（本文总目标）**：用运行时合同把「意图 → 围栏 → 验收 → 状态」做成可履约流程；每一轮小步、可验、可合并，质量叠出来——**不是**靠长规范当用户合同，也**不是**幻想一次对话出完整大产品。  
1. **安全围栏**：明确「这一轮只准动哪些路径、跑哪些命令、花多少预算」；越界必须被拦下，不能靠模型自觉。  
2. **可审计**：谁批的、批的是哪一版合同、验过哪些命令、证据在哪——事后能翻。  
3. **对老项目救命**：导入已有仓库后，合同把「批量退款」之类新需求关进新文件/指定路径，**默认不准乱动登录、支付、密钥**（再叠加保护清单 P.1）。  
4. **与防假绿对齐**：合同授权「可以施工」；绿灯（点亮）仍只认三件物理证据（受控写入 + 验证退出码 0 + 指纹），合同本身**不发绿灯**。  
5. **非技术友好**：用户面对的是「确认原型 / 同意吗 / 合并」，而不是去填 JSON；复杂字段由 Supervisor / Daemon 生成并校验。

### 1.2 非目标（合同不管什么）

- **不管**「项目全景」怎么从代码里读出业务脑图（那是全景分析链，v0.2）。  
- **不管**自由模式里未碰锁的日常微调是否弹窗（自由模式无正式合同门槛，但碰锁必问；可有静默备案）。  
- **不替代**保护清单：锁是「碰这里必问」；合同是「这轮围栏有多宽」。两者可同时生效。  
- **不保证** AI 写对业务：合同保证边界与检查门槛，对错仍靠验收、质疑与证据。
- **不替代**两份大规范：造 Stagent 本身仍用《架构规范》《任务规范》+ 人工四件套；本文只描述产品给**普通用户**用的运行时护照。

### 1.3 Dogfood 镜像（一句）

人工版「大规范 + 小任务卡 + Worktree + 真测试合入」养出 Stagent；产品版把同一套纪律自动化成「聊天提纯合同 → 灰图 → 三证点绿 → 合并」——用户吃的是你亲手跑通的工程防御智慧，不是轻浮的「模型一次写完」。

## 2. 原理（How · 设计哲学）

### 2.1 意图 ≠ 授权（架构铁律）

```
右侧聊天把想法说清楚          → 意图（requirements / Demo）
中栏点「确认原型并实施…」     → 显式批准开工（标准通道）
合同 JSON 落盘 + 状态机前进   → 机器可执行的授权
Worktree 内 Scoped 写入       → 围栏内施工
验证 + Evidence               → 可合并的客观证据
用户点「合并」                → 入主干（核销）
```

用户「觉得 Demo 好看」**不等于**「批准破坏性权限」。标准通道必须显式批准；轻量 Fast Path 必须以**系统留痕 + 可撤销快照**为底线，且越权立即熔断升回标准审批。

### 2.2 Schema 即宪法

全工程唯一合同契约在：

- `src/lib/contract.schema.ts`（Zod，`SoftwareContract` / v1.3.0）

Daemon 存盘、迁移、审批、执行前都会 `parse`；非法组合（例如未批准却进入执行态）直接拒绝。架构 §9.1 是目标模型说明；**以 Schema 与测试为准**对照实现。

### 2.3 双状态机联动

合同同时有两套状态，必须成对合法：

| `lifecycle_state`（生命周期） | `approval.status`（审批） | 白话 |
| --- | --- | --- |
| `DRAFT` | `DRAFT` | 还在谈方案 / 玩 Demo |
| `PENDING_APPROVAL` | `PENDING_REVIEW` | 等高风险或保护项勾选批准 |
| `PREPARING` | `APPROVED` | 已获批：建 Worktree、挂 Scope、准备图 |
| `EXECUTING` | `APPROVED` | Worker 在围栏里改代码 |
| `VERIFYING` | `APPROVED` | 跑检查 |
| `PENDING_RESUME` | `APPROVED` | 预算/重试耗尽等，等你恢复 |
| `AUDITED` | `APPROVED` | 检查过关，可真机试玩 / 准备合并 |
| `MERGED` | `APPROVED` | 已合入主干（终态） |
| `ABORTED` | `REJECTED` 或保留历史 `APPROVED` | 驳回或放弃（终态） |

**升版规则**：Scope / 命令白名单 / 预算 / 网络 / Worker / 验证命令一变 → `contract_revision` +1 → 审批强制回到 `PENDING_REVIEW`，**禁止拿旧批准偷跑新范围**（防 TOCTOU：`approved_revision` 必须对上当前版本）。

### 2.4 三通道准入（风险分级）

| 通道 | 何时 | 要不要你点批准 | 留痕 |
| --- | --- | --- | --- |
| **Fast Path（轻量）** | 单文件 ∩ 文案/样式类 ∩ 无命令 ∩ 无依赖 ∩ 未碰保护清单 ∩ 自由模式 | 系统自动签发（`system:fast-path`） | 必须有 `ADMITTED_AUTOMATIC`；可撤销；越权熔断升标准通道 |
| **标准通道** | 常见功能开发 | 确认原型 / 显式批准 | 完整合同 + Evidence |
| **高风险通道** | 命中保护清单、认证/支付/库表、外网/依赖等 | 专项安全卡，逐项勾选 | 禁止静默放行 |

> 实现注意：状态机要求 Fast Path 走 `DRAFT → PREPARING → EXECUTING`，**禁止** `DRAFT → EXECUTING` 直跳，以便先建好隔离现场。

### 2.5 正式合同 vs 静默合同 vs 证据

| 概念 | 是什么 | 用户感不感觉得到 | 能不能当合并依据 |
| --- | --- | --- | --- |
| **软件合同** `SoftwareContract` | 审批过的围栏 + 意图 + 验证 | 合同操作台 / 批准卡 | **能**（配合 Evidence） |
| **静默合同** `.stagent/silent-contracts.jsonl` | 自由模式后台备案：本轮开始/快照/决策/关闭 | 前端无感 | **不能** |
| **证据包** Evidence | 验证结果、指纹、范围校验等 | 验证输出 / 合并门禁 | **合并硬门槛** |

P.1 白话稿原话：自由模式 =「没有合同门槛，但碰锁必问」；正式 Evidence 主要出现在保护模式走正式流程时。

## 3. 生命周期（从想法到合并）

### 3.1 标准八步旅程里合同出现在哪

对齐架构 §0.2 与任务图谱说明：

```
1 右侧澄清需求（requirements.md）
2 中栏 Demo 假页面试玩（隔离 Origin，不碰真仓）
3 【确认原型】→ 合同批准 / 进入 PREPARING → 落全灰任务图
4 Worktree 内按图施工（EXECUTING）→ 验证（VERIFYING）
5 真机试玩 + 证据全绿 → AUDITED
6 可选：质疑自查（修复不得偷偷扩 Scope）
7 增量需求 → 合同升版重批
8 再确认原型 → 图上追加灰节点 → 循环
```

**合同是第 3 步之后「真动手」的通行证**；第 1～2 步可以没有已批准合同（草案阶段 `DRAFT` 常见）。

> **聊天不整段进拆解**：右侧对话用于澄清；Supervisor 通常按**当前意图**生成/更新合同草案。真正驱动「确认原型 → 全灰任务图」的输入是**合同里的意图与围栏**，不是把整段聊天记录当任务清单。闲聊不建图。

### 3.2 机器侧主路径（实现）

1. **生成草案**  
   - `createContractDraft(...)` / Supervisor `generateContractDraft`  
   - 写入意图、可写路径、验证命令、预算、默认 Git 禁旗、Worktree 分支名 `task/<contract_id>`  
2. **落盘**  
   - `ContractStore.save` → `.stagent/contracts/<contract_id>.json`（原子写 + Schema 校验）  
3. **提交审批 / 准入**  
   - `submitDraftForApproval` → `PENDING_APPROVAL`  
   - 或 `admit` / Fast Path 系统批准 / `approve(contractId, reviewer)`  
4. **准备现场**  
   - `PREPARING`：建任务 Worktree、挂 Scoped Gateway、（确认原型后）落 `task_graph.json`  
5. **执行与验证**  
   - `execute` / `run-worker`：合同锁互斥；命令与写入走白名单；未跟踪文件 Scope 守卫（W.2b）  
6. **审计与合并**  
   - `AUDITED` → 用户合并 → `MERGED`；或 `abort` → `ABORTED`  
7. **异常**  
   - 外部改码 → 图节点待重验 + 合同可降级回 `VERIFYING`；挂起可 `healResume`

### 3.3 用户可见的最少操作（心智）

对非技术用户，标准通道尽量收成：

1. 聊清楚 + 点点假页面  
2. **确认原型并建图 / 实施**（批准本轮围栏）  
3. （高风险时）再点一张「同意碰锁」卡  
4. 检查绿了之后点一次 **合并**

同意 ≠ 合并：同意是动手前授权；合并是验收后入主干。

## 4. 与全景 / 施工解耦

> 权威产品叙事见：`docs/reports/任务图谱-设计说明-2026-10-24.md` §9.9（买二手房）。

## 5. 安全边界（尤其改老项目）

### 5.1 文件围栏（Scope）

合同里（实现字段）大致是：

- `authorization.file_system_scope.writable_paths`：本轮**准写**（至少一条，空 Scope 直接拒）  
- `readonly_paths`：可读参考  
- `strictly_forbidden_paths`：死线（默认常含 `.env*`、`**/.git/**`、锁文件等）

路径必须相对仓库根，禁止 `../` 与绝对路径开头（Schema 硬校验）。

**改老项目时的产品含义**：  
「只准动退款相关新文件 / 指定路径，不准动登录和支付」——就是把登录/支付放进禁止区或根本不放进可写列表；再叠加 P.1 保护清单，碰锁必弹同意卡。

### 5.2 Git 围栏

- 强制 Worktree 隔离（v0.1：`use_worktree: true` 语义）  
- 允许操作白名单（status/diff/add/commit/checkout/branch/merge 等；**默认不含 push/reset/clean**）  
- **强制禁用参数**（任何配置不可拿掉）：`--force` / `-f` / `--hard` / `--amend` / `--no-verify`  
- 可选 `enforce_clean_base`：脏基线要显式确认（注意：`stagent open` **不要求**主分支干净；脏检查在 Worktree/合并侧）

### 5.3 命令 / 网络 / 预算

- `execution_permissions`：允许的命令别名、环境变量名、网络策略（默认 `DENY`）、是否允许改依赖（默认否）  
- `budget_limits`：改文件数、diff 行数、时长、验证重试次数等；超限熔断  
- `cost_limits`：费用上限（最小货币单位）  
- `verification_spec.commands`：结构化 argv（可执行文件 + 参数数组），**禁止**随意拼 shell 字符串，降低注入歧义

### 5.4 执行闸门（谁在拦）

- **Scoped MCP / Gateway**：Worker 写文件、跑命令先过网关  
- **未跟踪文件 Scope 守卫**（`untracked-scope-guard.ts`）：防「没走网关却 `git add -A` 把野文件捎进提交」  
- **保护清单门卫**（P.1）：锁路径先拦后写；不同意则零写入  
- **合同互斥锁**（`contract-mutex`）：同一工作区避免两轮正式施工踩踏  
- **UNCONTROLLED_EXTERNAL** Worker：Schema 禁止进入可执行生命周期，不得产可合并证据

### 5.5 修复与质疑时的扩权 ban

架构要求：判定「实现偏差」自动修时，修复目标必须是**原合同 Scope 的确定性子集**；超出必须**合同升版重批**，禁止 Supervisor 隐式扩权。

## 6. 数据结构与关键路径

### 6.1 合同 JSON 核心字段（白话对照）

| 字段 | 白话 |
| --- | --- |
| `contract_id` | 本轮身份证，例如 `contract_1792607266038_110hd` |

## 7. v0.1 现状与已知限制（诚实边界）

### 7.1 已落地（可对外说）

- Schema v1.3.0 双版本解析、草案创建、升版重批、Git 强制禁旗、执行态必须已批准等不变式（有单测）。  
- 合同存盘、列表、批准、执行编排、中止、证据与合并管道。  
- 确认原型 → 从合同拼全灰图并落盘（S.6）；图谱开工/核销入口（C.10o）；合入清树后 Worktree 自愈（C.10p）。  
- Fast Path / 自动准入留痕方向（`system:fast-path` / admit）；保护清单 + 静默合同流水（P.1）。  
- 未跟踪 Scope 守卫、合同锁、Gateway 强制控制模式。  
- Studio 全景/施工双视角：施工侧强依赖本轮合同与图；全景禁绿。

### 7.2 规范有、实现未齐或易误读

- 架构 §9.1 文内仍有「待实现」历史标注；部分目标字段（如顶层独立 `scope`、`presentation_state` 持久化形态、`SANDBOX_ENFORCED`、完整 `EvidenceBundleV12`）与代码字段布局不完全同构——**以 `contract.schema.ts` 与测试为准**。  
- 自动批准路径上可见 `stagent-auto` 等审阅者标识（dogfood/编排）；与规范里的 `system:fast-path` 称谓并存时，以 Schema 校验规则解释「谁能签 `ADMITTED_AUTOMATIC`」。  
- 「一键无人值守从确认原型到自动点亮」仍有体验缺口：图谱可开工/核销，但日常项目级 Worker 适配与自动点亮流畅度仍在补。  
- v0.1 全景**不是**「无合同也能全仓脑图」；那是 v0.2。  
- 产品侧弱点仍在（与 §0.3 对齐）：拆解偏机械、复杂架构要人拍板、进门真全景未齐——开发过程的 dogfood 证明纪律有效，**不等于**这些弱点已从产品消失。  
- 合并后再对旧图核销：可重建 Worktree，但产品上应避免误导为「还能改已合并主线」而不开**新合同**。  
- 图与合同一对多心智：磁盘权威图通常挂一份 `contract_id`；UI 选错合同会像「没图」。

### 7.3 安全下限 ≠ 高质量上限（6 项质量方向 · 校正版）

> 来源：t700u 分析 + t701u 校正写入。**本节是规划与诚实对账，不在本文改产品代码。**

#### 7.3.1 一句话定调

现有《合同设计说明》与实现，首先是一套**面向 AI 自动编码的安全防守 + 可履约流水线**（意图与授权分离、文件/命令圈地、三证防假绿）。这保住了**安全下限**：AI 不易把老项目改崩，也不易拿口头报喜骗过图谱。

但「防破坏围栏」≠「商业级高质量交付保证」。要把合同升级成更完整的**自动化交付质检标准**，还须补「测得深、圈得准、红了能自愈、真机能验收、撤场零污染」——其中多数不是「完全没有」，而是**半有底座 + 缺写清/强制的质量条款**。

| 现有文档做得好的（安全下限） | 还不够支撑「高质量可交付」上限的 |
| --- | --- |
| 聊需求 ≠ 准改代码 | 退出码 0 挡不住「水测试」 |
| `writable_paths` / 禁区护地基 | Scope 推导仍偏机械（#3 确缺） |
| 三证核销，不听模型口头汇报 | 回归 / 自愈协议 / 真机强制 / Abort 清场仍须加强 |

#### 7.3.2 六项对照（勿写成「完全没有」）

| # | 方向 | 现状定性 | 已有底座（勿抹掉） | v0.2+ 要加强什么 |
| :- | --- | --- | --- | --- |
| **1** | 验收规格增强（防「假测试 / 水测试」） | **半有** | 有结构化 `verification_spec`；施工围栏与 Scope 可限制乱改测试文件；三证要求真跑命令且退出码 0 | **不能**说「完全没有防改测」。缺的是：断言密度/业务测质量门槛；明确「业务测由谁生成、施工期 Worker 可否改断言」；挡住 `expect(true).toBe(true)` 这类敷衍绿 |
| **2** | 全仓回归门禁（防改坏老地基） | **半有** | 默认验证链路常会跑项目既有测试（如 `npm test` / typecheck）；合并侧有证据与门禁思路 | **不能**说「合同完全不管老功能」。缺的是：合同合并条件里**强制**「既有回归基线（Baseline Suite）退出码必须为 0」的硬条款；避免合同把验证**缩窄**成只跑本轮增量测就放行 |
| **3** | 代码影响面推导（智能化 Scope） | **确缺** | 目前 `writable_paths` 多靠 Supervisor / 规则偏机械拟定；撞墙靠网关拦截与升版重批补救 | **这是六项里最干净的缺口**：须结合 AST / 依赖调用图 / 路由反查做影响面分析，再填 Scope；提高一次通过率，减少漏圈/圈多 |
| **4** | 施工期自愈协议（红灯→修→再测） | **半有** | `budget_limits` 已有验证重试次数等预算；超限可熔断 / `PENDING_RESUME`；失败可挂起再 `healResume` | **不能**说「完全没有重试」。缺的是写清的 **Red-Green 内部循环协议**：写码→跑测→读日志→围栏内修复→再跑；最大次数；失败时**禁止**为过关而篡改验收断言；超限才挂起人工介入 |
| **5** | 真机实测交付门禁（试新车） | **半有** | `AUDITED` 后已有真机预览/试玩方向（八步旅程「试新车」）；区别于前期隔离 Mock Demo | **不能**说「只有 Mock、没有真机」。缺的是：把「用户在真实运行态点过【验收通过】」做成进入 `MERGED` 的**可选或强制门禁**（产品策略待定），而不是只看终端日志 |
| **6** | 失败原子回滚（零污染撤场） | **半有** | `ABORTED` 路径会处理合同终态；Worktree 清理 / 合入清树后自愈（如 C.10p）已有进展 | **不能**说「abort 完全不清理」。缺的是写清并补齐：`git worktree remove` 强制策略、未跟踪逃逸扫描抹除、端口/锁文件/临时进程等副作用清场清单，保证工作区恢复如初 |

#### 7.3.3 建议写入合同制度的条款方向（规划，非本轮实现）

1. **`verification_spec` 质量条款**：业务测试所有权（谁生成）、施工期是否只读测文件、可选断言密度/覆盖门槛——防放水，不是重复发明「要跑测试」。  
2. **合并条件显式回归**：除本轮增量证外，既有 Suite 必须同绿才准 `MERGED`；合同不得轻易把回归缩成空集。  
3. **Scope 影响面（#3 优先立卡）**：Supervisor 拟定可写路径须有依赖/路由依据；机械猜名降为兜底。  
4. **`EXECUTING` 内 Red-Green 协议**：次数、日志回灌、禁改验收断言、超限→`PENDING_RESUME`。  
5. **`AUDITED`→用户真机确认→`MERGED`**：与 Mock Demo 分栏呈现；策略可「高风险强制 / 常規可选」。  
6. **`ABORTED` 清场协议**：Worktree + 未跟踪逃逸 + 端口/锁/垃圾文件检查表；与现有清理能力对齐后补洞。

#### 7.3.4 与其它 v0.2 方向并列（不在本文实施）

- 真·进门全景三卡与只读扫描链（不依赖本轮合同）。  
- 合同呈现进一步白话化（少暴露 JSON 字段名）。  
- 更完整的高风险专项授权卡与委托审批等（若 RFC 收录）。  
- 文件夹弹窗打开项目（D.1e）等进门体验。  
- **上表 6 项质量上限**（尤其 #3 Scope 影响面）——立卡时须写清「半有 / 确缺」，禁止把已有底座写成空白。

## 9. 给 Tina 的八句收口

1. **本文不是空概念**：设计的是「本轮可交付改动」如何用运行时合同高质量履约（意图 / 围栏 / 验收 / 状态）。  
2. **宪法 vs 护照**：两份大规范造 Stagent；运行时合同是用户每次需求的机读小卡 JSON，不是几十页 Markdown。  
3. **合同 = 本轮改代码的安全授权说明书**：写清做什么、准改哪、怎么验、谁批过。  
4. **聊天不整段拆任务**：进拆解的是合同；确认原型后落灰图；绿灯靠三证，合同本身不发绿灯。  
5. **和全景解耦**：摸家底不需要合同；要改代码才签合同、建施工图。  
6. **能力边界**：能叠出可控可验收增量；不等于一次出顶级大系统；**安全下限≠高质量上限**——六项质量方向见 §7.3（仅 #3 确缺，其余半有）。  
7. **Dogfood**：人工规范 + 四件套养出产品；产品把纪律自动化给用户。  
8. **今天**：正式合同链路已能用（安全下限）；全景真三卡、Scope 影响面、防用水测/强制回归/自愈协议写清等仍在后续——别把占位或半有底座说成「完全没有」或「已经完工」。
