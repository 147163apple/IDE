## 2. 与现行安全面冲突的提案（需撤回或降级）

### 2.1 新增 `stagent_grep_search` / `stagent_file_glob` —— 与 A §4.1 冲突

- **事实**：受控工具集在 v1.3.3 中已**统一为 6 项**（变更摘要 §2.1 表格第 32 行），实现见 `daemon/worker/worker-toolset.ts`：
  `stagent_read_file` / `stagent_write_file` / `stagent_list_directory` / `stagent_delete_file` / `stagent_exec_command` / `stagent_declare_complete`。
- **冲突点**：
  1. 每新增一项工具 = 新增 Gateway 路径校验、threat-guard 负例、`scope_audit` 与 E.1 故障用例的一整条攻击面，基数从 6 变 8 需同步修订 A §4.1。
  2. W.5a 路线下 Claude Code **保留原生工具**（`claude-code-adapter.ts` L63–72 `BASE_TOOLS` 已含 `Glob` / `Grep`），检索能力已由受控原生工具提供。
  3. 保底轨（自研 API Worker）与前瞻轨（cli-host）能力不一致会造成**双轨漂移**。
- **建议**：不新增。若保底轨确需检索，单独立项为 v0.2+，并同步修订 A §4.1 基数与 B W.1 用例。

### 2.2 落盘路径 `.stagent/run/<task_id>/config.json` —— 劣于现行实现

- **现行实现更优**：落在 `os.tmpdir()` 下的 `mkdtemp` 目录，**不进 Worktree、不进 git、不进 `.stagent` 保护/禁读区**。
- **报告提案的风险**：
  1. `.stagent/**` 在 `claude-code-adapter.ts` L119–134 的 `deny` 列表中是**硬禁写/禁读**，Worker 侧写此处会触发不必要的策略违规；
  2. 落在工作树内会参与主树 dirty 判定与 Evidence 指纹复核链路（B B.2 L640、A §6.4）；
  3. `protection-list.ts` 的路径 glob 与 chmod 纪律也会额外受限。
- **真实缺口（可补）**：`tmpRoot` 未显式注入时落入共享临时目录，若进程崩溃导致 `rmSync` 未执行会**残留**。建议增加启动期 GC 扫描 `stagent-claude-*` 陈旧目录。
  → 这才是值得写进报告的那一条。

### 2.3 「TTF v0.2+ 将 Process Host 下沉 Rust」—— 与既定边界冲突

- A §4.2.3 / B §3.3 W.1 F 组规定：`daemon/worker/cli-host/**` 是全仓**唯一**允许 spawn 的模块。下沉 Rust 会引入第二个 spawn 宿主。

### 2.4 Profile / Bundle 分层与 TTL Eviction —— 属于新提案，不是纪律

## 3. 取证章节的方法论修正

| 报告原文 | 问题 | 修正建议 |
|---|---|---|
| 标题「**五大**深层根因」，正文只列 **4** 条 | 文档自洽缺陷 | 改为「四大」或补齐第 5 条 |
| VSZ `1890551472` KB（≈1.76 TB）与 RSS 并列 | macOS Electron 的 VSZ 是虚拟地址空间，**常态即为 TB 级**，不构成内存证据 | 从证据表中移除 VSZ 列，或加注说明 |
| RSS 2,016,048 KB ⇒ 「2GB 内存**泄漏**」 | 单次快照只能证明「驻留高」，无法证明泄漏（无单调上升趋势、无 heap snapshot） | 改为「驻留偏高」；补 ≥3 次间隔采样或 `footprint`/堆快照才能定性泄漏 |
| 「单核 **持续**占满 103.8%」 | BSD/macOS `ps` 的 `%CPU` 是**衰减加权平均值**，单点无法证明「持续」 | 补 `TIME` 增量对比：两次采样间 CPU 时间增量 / 墙钟时间 ≈ 目标占比 |
| `%MEM 4.0` 与 RSS 2GB 并列 | 隐含物理内存约 50 GB（48/64 GB 机型），脱离机型则 2GB 的严重性被误读 | 注明机型与采样时已开机时长 |
| 无头 Edge PID 81095 / 81109、端口 9333 归因为 Electron 拉起 | ps 快照未给出 **PPID**，父子关系未被证明 | 补 `ps -o pid,ppid,command` 或 `lsof -i :9333` 佐证 |

> 结论不受影响的方向依然是成立的：Electron 宿主 + 重型 Node CLI + 多 MCP 长连接确实是高能耗组合。但**证据强度需要从「单次快照」升级到「多次采样」**，否则作为决策依据会被推翻。

### 6.2 残余问题清单

**R-1 · 证据力仍有缺口：占空比未被归一（中）**

v3.0 §三.2 写「累计 CPU 时间 9 分 17 秒，证明该进程**曾长期处于重负载**」。
`TIME` 是**生命周期累计值**，不含墙钟分母。若进程已运行 12 小时，9m17s 折算占空比约 1.3%，不构成「长期重负载」。

修正建议：补 `etime` 后按占空比判定。

```bash
ps -o pid,etime,time,%cpu,rss,command -p <PID>
# 占空比 ≈ TIME / ELAPSED；> 50% 方可称为"持续高负载"
```

// P.1：待审批卡要"立刻"出现（AI 被拦在原地），保护状态单独 3s 轮询

### 7.2 残余问题

**N-2 · 中：RSS 单位换算错误（本轮修正确引入）**

v3.1 L56 写「RSS 约 **2,016 MB**」。`ps aux` 的 RSS 列单位为 **KB**，故 `2016048 KB = 1,968 MB（1.92 GiB）`。
同时 §三.1 的采样表格未给 RSS 列标注单位。建议：表格补 `RSS(KB)` 表头，正文写作「约 1.97 GB（1,968 MB）」。
（注：L59 的占空比示例 `557s / 43200s ≈ 1.3%` 经复核计算正确。）

**N-3 · 中：判据①与既有性能基线冲突**

R-4 判据①「Daemon 主线程任意单次同步计算 ≤ 50ms」与 B §3.5 TASK-B.1 既有基线「冷启动 ≤1.5s、单文件增量 ≤20ms」直接冲突——若 v0.2+ 恢复 B.1，其冷启动预算本身就超限一个数量级。
建议收窄作用域为「**请求处理路径上的**单次同步计算 ≤50ms」，并显式声明：B.1 恢复时必须移出主线程（worker_threads / 分片 yield），否则两条判据不可同时成立。

**N-4 · 低：「3s Debounce」的上下文不止两处**

v3.1 L105 将其二分为「Supervisor 侧听轮询」与「Monaco 编辑器防抖」，实际仓库内共三处语义：
1. Supervisor 侧听节流——且 **B §1.1 L25 已把「3s Debounce」写进 TASK-S.1 的 PASS 验收判据**，故不能说它与 Supervisor 完全无关；
2. A 版本头第 4 条「Monaco 服务端 403 校验与 3s Debounce 节流基线」（`daemon/editor/` 下未见实现，当前仅文档基线）；
3. 前端 `fetchProtection` 的 3s 轮询（见 N-1）。

**N-5 · 低：命名歧义**

v3.1 §七.1「AST 零工具守卫」中 AST 指的是 lint 手段而非对象，易被读成「AST 工具数为零」。建议改为「Supervisor 零工具回归守卫（AST 依赖扫描）」。

**N-6 · 低：公式渲染**

v3.1 L60 使用 LaTeX `$ \text{Duty Cycle} = \text{TIME} / \text{ELAPSED} $`，普通 Markdown 渲染器不识别 `\text{}`。建议改为行内代码：`` Duty Cycle = TIME / ELAPSED ``。

### 7.3 结论

v3.1 已吸收全部 5 项残余建议，除 N-2 单位换算外无新增事实错误。当前唯一实质性发现是 **N-1**：三个版本的报告都在讨论「禁止常驻轮询」，却始终没有发现前端那条硬编码的 3s 轮询。建议将其连同 `/api/arch/graph` 一并登记进 `docs/reports/W3-待办-已知缺口.md`。
