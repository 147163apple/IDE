## 2. 真实链路度量

### 2.1 主流程耗时（1 次真实自举，`hrtime` 实测）

| 阶段 | 耗时 | 说明 |
| --- | --- | --- |
| 准入 + Worktree 创建 | **338 ms** | `admit()` 内含准入判定、Worktree 创建、依赖视图挂载、状态机两次跃迁 |
| 受控写入 | **23 ms** | 3 个文件经网关写盘（含范围校验、预算计数、审计日志） |
| 命令验证 | **3 577 ms** | `npm run typecheck` 2 484 ms + 定向单测 729 ms + 编排/审计开销 364 ms |
| 合并 + 现场清理 | **241 ms** | 五道门禁 + `git merge --squash` + Trailer 提交 + `worktree remove` + 分支删除 |
| **全流程合计** | **4 216 ms** | 从合同落盘到现场清理完毕 |

> 说明：本次验证跑的是整仓 `tsc --noEmit`（2.5 s 量级），因此验证段占了总耗时 85%。这是「真跑类型检查」的代价，不是流水线本身慢。

### 2.2 Worktree 创建 / 销毁（独立微基准，3 次）

主流程里 Worktree 生命期被 `admit()` 与 `squashMerge()` 包住，无法在不改生产代码的前提下单独埋点，因此用「准入 → 立即中止」的极短合同做独立测量（`scripts/worktree-bench.ts`）：

| 指标 | 样本（ms） | 均值 |
| --- | --- | --- |
| Worktree 创建 | 288 / 258 / 256 | **267 ms** |
| Worktree 销毁 | 129 / 132 / 128 | **130 ms** |

微基准含依赖视图挂载（共享 `node_modules` symlink）与 PID 锁；**未安装依赖**（锁文件一致 + 写保护可证明 → `SHARED_SYMLINK`）。若换成一棵需要独立安装依赖的仓库，创建耗时会从百毫秒级跳到分钟级——本数字**不可外推**为通用性能承诺。

### 2.3 Token / 费用统计（如实：本次为 0）

Evidence 的用量字段（原样摘录）：

```json
"usage": { "currency": "CNY", "pricing_version": "unpriced-v0", "accounting_mode": "UNAVAILABLE", "limit_reached": false }
```

- **没有 API Key 直连用量可报**：本次改动由确定性 `modelClient` 产出，未调用任何外部模型，因此 Token = 0、费用 = 0，证据里 `accounting_mode` 就是 `UNAVAILABLE`。

## 4. 如实披露：客观局限与已知残余

### 4.1 本次演练没有做的事（最重要的一条）

**没有真实大模型参与生成。** 环境无 `OPENAI_API_KEY`，`modelClient` 是确定性实现（按锚点做定点替换）。它与真实模型**共用同一条通道**——同样的 `AiWorker`、同样的范围校验、同样的网关写盘、同样的证据与门禁——但它不是模型，"模型能改对代码"这件事本轮**没有被验证**，也不能据此外推。
若要做真机验证：置好 `OPENAI_API_KEY` 后重跑 `npx tsx scripts/dogfooding-run.ts`（需把脚本里的确定性客户端换成 `OpenAiWorkerClient`），届时 `usage` 才会有真实数字。

### 4.2 前期已登记、本轮仍未闭环的残余

| # | 残余 | 影响 | 现状 |
| --- | --- | --- | --- |
| R-1 | `TASK-C.2` Studio 面板内不能直接改合同 Scope（需重建合同） | 体验：改范围要重走一次准入 | 未排期（v0.2+） |
| R-2 | Protected 模式「授权粒度」不一致：准入/拒绝以合同 scope 字符串为键，写闸门按具体路径精确匹配 | 合同写 glob 且命中保护清单时，用户同意后仍可能**再弹一张卡**（安全无损，违背「≤2 次交互」） | 已记录，待修（建议 `guardAgentWrite` 对 `approvedFiles`/`deniedFiles` 做 glob 匹配） |
| R-3 | 网络 `DENY` 是**非对抗性离线约束**（ADR-003） | 只降低误联网概率，不构成对恶意代码的强制隔离 | 设计如此，须在发布说明中如实表述 |
| R-4 | 单任务串行、仅 macOS 实测、未在第三方真实项目试用 | 并发与跨平台未验证 | 沿用旧版结论，未变化 |
| R-5 | 模型适配器边界：`GATEWAY_ENFORCED` 为内置受管模式；外部 CLI（Claude Code / cursor-agent / OpenHands）各自 `verified_on` 口径未在本轮复测 | 不能声称「所有 Agent 均已受控」 | 见 §5 |

| # | 缺陷 | 证据 | 处理 |
| --- | --- | --- | --- |

## 6. 发版与构建

| 项 | 结果 |
| --- | --- |
| 版本号 | `package.json` → **0.1.0**（`package-lock.json` 同步） |
| 构建命令 | `npm run build`（`vite build` + `postbuild` 装配 `dist/`） |
| 构建结果 | **0 error**，`dist/` 33 个文件 / **3.15 MB**（前端 4 个 / 1.00 MB，后端 25 个 / 2.15 MB） |
| 构建指纹 | `dist/BUILD-INFO.json`：版本 / 提交 / 分支 / 时间 / 各目录文件数与字节数 |
| 入口 | `dist/server/index.mjs`（后端）、`dist/public/assets`（前端静态资源） |
| 测试 | 全量 **785 passed / 6 skipped**（86 文件通过 + 1 skip），零失败 |

> `.output/` 是框架（nitro）的部署产物，`dist/` 是发版产物；两者同源，`dist/` 由 `postbuild` 装配并附构建信息。
> `postbuild` 处置旧 `dist/` 的方式是**先整体移入系统临时目录**（`stagent-dist-<ts>`，等价回收站，零删除动作；跨卷不可 `rename` 时退回逐项删除）。原因：部分宿主 / CI 对批量删除设有阈值保护，一次性删 70+ 条目会被直接拦下，导致 `npm run build` 在最后一步失败、`dist/` 停在半更新状态；实测「逐项删除」只是把 70 次删除摊开，遇到按**累计次数**计数的保护同样会撞线（构建日志见过 `count:50, threshold:50` 被拦）。发版构建不应因清理动作失败。

## 7. 结论

在 Stagent 自身仓库上，`合同 → 准入 → 隔离 Worktree → 受控写入 → 真实命令验证 → Evidence → 五道合并门禁 → 带 Trailer 的进入主干 → 现场清理` 这条链**真实跑通并留下可独立复核的证据**：耗时 4.2 s、一次过（0 重试）、证据哈希可被 `shasum` 复算、现场无残留。

同时必须说清三件事：
1. **没有真实模型参与**——"AI 改对代码"这件事本轮未被验证；
2. 本次自举与随之而来的门禁复跑，共翻出 7 个真实缺陷（N-1…N-7）：4 个当场修复（陈旧 `dist/`、缺 `version` 字段、会话用例端口与时序假失败、构建清理被批量删除保护拦下），2 个如实标注为未修的已知问题（`files_changed` 丢失、`diff_stat`/`patch_fingerprint` 空值），1 个是规范文本口径差异；
3. v0.1 的边界是「本机、单人、单任务、可回滚」，跨平台与并发未验证。
