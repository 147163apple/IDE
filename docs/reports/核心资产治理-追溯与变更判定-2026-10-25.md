# Stagent 核心资产治理、追溯链与轻量变更判定规范

**版本**: v1.0.0（层 C 定稿）  
**日期**: 2026-10-25（Asia/Hong_Kong）  
**定位**: 层 C 核心设计说明与对账准则（与《合同设计说明》《Supervisor运转机制》同级）  
**边界**: 本文件指导**运行时资产治理与门禁**；**不替代**《架构规范》《任务规范》。工程落地须经 Tina「立卡」后写入任务规范，再按现有 DAG 施工。  
**核心公式**: **意图对齐 = 需求断言 → 合同护照 → 隔离 Demo → Evidence 闭环**

**适用范围**: 用户明确要改码时的「本轮施工图」链路。仅导入、只读「项目全景」、无改码意图时，合同 / Demo / Evidence 链**整段不适用**（只做勘察，不强制本规范门禁）。

## 一、六类核心资产的生命周期矩阵

| 资产名称 | 1. 创建 | 2. 冻结 / 生效 | 3. 变更 | 4. 归档 | 责任人 | 典型触发场景 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **1. 架构规范**<br>*(层 A·施工宪法)* | 产品规划拍板后定稿 | 版本号锁定（如 v1.6.1） | 仅 RFC/立卡后升版；日常施工不改 | 旧版进 `docs/archive` | Tina 拍板；Supervisor 起草 | 分层/安全不变量变了 |
| **2. 任务规范**<br>*(层 A·施工宪法)* | 与架构配套立 DAG | 卡状态进施工前 Scope/验收定死 | 「立卡」增补；已开工卡不改验收文 | COMPLETED 卡保留痕迹 | Tina「立卡」；Supervisor 写卡 | 新能力/修缺口 |
| **3. 需求断言**<br>*(层 B·运行时交付)* | 右栏澄清 → Supervisor 写出可观测条目 | 用户点「冻结本轮」→ `FROZEN` | 新意图开新快照，旧快照只读；**轻改**见 §三（仅文案/举例、不进阻断哈希） | 项目结项或轮次作废 | 用户确认；Supervisor 维护 | 「还要加/改一句需求」 |
| **4. 合同护照**<br>*(层 B·运行时交付)* | Supervisor 从冻结需求编译 JSON 卡（可与 Demo 并行拟稿） | 用户一键授权/签署（须满足下方时序） | 改 Scope/验收 → 旧约 `REVOKED`，发新约 | 生命周期到 `REVOKED` / `EXPIRED` | 用户签；Supervisor 拟约 | 授权范围或验收变了 |
| **5. 隔离 Demo**<br>*(层 B·运行时交付)* | 可与合同拟稿并行出 Mock | 用户「感官对齐」确认 | 需求/合同变了必须重生或标过期 | 本轮交付后可丢，保留引用哈希 | Supervisor 生成；用户验收感官 | 业务流程/界面承诺变了 |
| **6. Evidence + 图谱**<br>*(层 B·运行时交付)* | 开工后按卡点亮 | 核销门禁通过即「本卡冻结证据」 | 重开工则灰掉重跑；禁手工涂绿 | 随合同轮次归档 | Coding worker 产出；Supervisor 校验 | 任务完成/质疑重做 |

### 本轮施工冻结时序（硬顺序）

```
需求 FROZEN →（合同拟稿 ‖ Demo 创建）→ Demo 感官确认 → 用户签署合同 → 才许开工写真实代码
```

- 创建阶段允许合同拟稿与 Demo **并行**，避免串行等待。  
- **禁止**理解成「先签合同再补 Demo」：未确认 Demo 不得进真实施工（见 §二硬门禁 2）。

> **责任分工一句话**:
> - **用户 (User)**: 只做冻结、签署、感官确认与质疑；
> - **Supervisor**: 管生成、编译、门禁与追溯；
> - **Coding Worker**: 只在已签合同的 Scope 里写码与交证据。

## 二、四件运行时资产的相互追溯与阻断硬门禁

### 1. 双向追溯链结构

- **正向推导**: `需求条目 ID` → 合同 `intent_ref` / 验收条款 → Demo 场景绑定同一 ID → Evidence 断言绑定合同 `contract_id` + 需求 ID → 图谱节点点亮。
- **反向倒查（出问题时）**: 点开 Evidence → 看它声称满足哪张合同 → 合同指向哪条冻结需求 → Demo 是否还对应该场景。

### 2. 阻断哈希约定（轻改前提）

门禁比对的「承诺哈希」**只锁可观测行为字段**（行为指纹），例如：可验收行为描述、验收口径、Scope 路径集合、Demo 场景节点/关键路径、verification 列表。

**不进阻断哈希**（从而允许「轻改零仪式」）：纯文案润色、举例、对内注释、非行为性说明。若实现误把全文正文纳入哈希，会导致轻改误阻断——实现时必须按本条约拆字段。

### 3. 阻断交付的不一致硬门禁（Hard Blockers）

遇到以下任一违规，系统物理阻断，禁止开工或禁止合入主干：

1. **需求已 FROZEN，但合同仍引用旧草稿 ID** → 禁开工。
2. **合同已签，Demo 未确认或 Demo 哈希与合同声明不一致** → 禁写真实代码（可继续改 Demo）。
3. **Evidence 通过，但断言不在本合同 verification 列表内**（超范围绿） → 禁合入，图谱不点亮。
4. **Evidence 声称的路径 ∉ 合同 `writable_paths` / 触碰 P.1 保护区** → 立即失败并发起 Dispute。
5. **用户质疑后，旧 Evidence 未作废却仍显示绿** → 图谱回灰，禁标「本轮完成」。
6. **多张有效合同对同一文件可写且互相矛盾** → 禁并行开工，先合并或撤销。

> **软告警不阻断项**: 文案语气差、Demo 皮肤与真页有小幅视觉差但交互流程一致、任务规范里尚未立卡的远期 RFC 项。

## 三、需求变更后的轻量判定原则

当变更发生时，Supervisor 弹出极简选择卡（业务场景选择题 + 推荐项，禁止开放式技术填空），前置核验三问：

1. **改的是「要什么」还是「怎么验」还是「能改哪里」？**
2. **本轮合同是否已签署？是否已有真实代码写入？**
3. **Demo 场景节点是否变了？**

### 1. 变更分类判定矩阵

| 变更类型 | 需求断言 | 合同护照 | 隔离 Demo | Evidence / 图谱 | 判定标签 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **文案/举例微调**（可观测行为不变） | 补丁修订；不进阻断哈希，可同版本小改 | **沿用** | **沿用** | **沿用** | **轻改** |
| **新增/删除一条可验收行为** | **新快照或解冻再冻** | **重签**（旧约撤销） | **重审**（相关场景） | 相关节点 **回灰重跑** | **重签** |
| **只改验收口径**（同一行为） | 条目修订并再冻 | **重签** verification | 场景可沿用，验收脚本重绑 | **重跑** 相关 Evidence | **重签验** |
| **只收紧/放宽 Scope 路径** | 需求可沿用 | **重签** Scope | **沿用** | 超原 Scope 的证据作废 | **重签权** |
| **大改业务流程** | 新轮次需求 | 新合同 | **必须重做 Demo** | 整图回灰 | **新轮次** |
| **纯实现 Bug**（意图未变） | **沿用** | **沿用** | **沿用** | 单卡重跑 Evidence | **返工** |

### 2. 变更三条铁律

- **铁律一（意图变了）**: 意图变了 → 需求至少再冻一次；已签合同一律撤销重签，严禁「口头改约」。
- **铁律二（感官变了）**: 感官变了（用户按 Demo 点的路径变了）→ Demo 重审；未确认 Demo 不得进真实施工。
- **铁律三（仅代码错了）**: 只有实现错了、四件资产的承诺哈希都没变 → 只重跑 Evidence，不惊动签署。

---

**落定结论**: 轻改零仪式，重签是默认安全档，新轮次整链重来。杜绝人肉扯皮，由（行为字段）哈希锁死意图。工程实现须另「立卡」，本文件本身不是施工单。
